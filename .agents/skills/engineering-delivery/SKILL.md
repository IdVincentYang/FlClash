# Engineering Delivery

## 1. 用途与触发

用本 Skill 组织或执行有明确交接关系的工程任务。
先确定当前角色、任务和所处阶段，只推进本次请求与授权覆盖的范围。
不要把一次设计、评审或状态查询解释成完成整个流程的授权。

首次应用时，先向用户明确说明本次使用 **Engineering Delivery**，并结合已核实信息
说明自己的具体名称、角色、任务与当前阶段；简短开场示例见
[启动说明](assets/lead-report.md#9-启动说明)。名称或任务归属尚未明确时说明待确认项，
按[协作协议 §1](references/collaboration.md#1-参与者身份)核实后再以该身份推进协作。
新参与者或身份／归属变化时告知变化；同一身份的正常续做不重复首次使用说明或名称确认。
每次任务报告仍须标注具体名称，不能把“不重复开场”理解为省略报告身份。

用户可以明确指定 `$engineering-delivery`、角色和任务，
也可以用自然语言描述需要的工作：

- 主控：“组织这轮迭代，协调现有开发者，审查设计和实现，确保符合阶段目标。”
- 执行者：“按任务计划完成这个功能，先向主控交设计，再按授权实施并汇报。”
- 评审：“开发者已完成任务，检查需求、架构与交付条件，给出评审结论。”

最后一种请求只进入评审阶段，不重启任务。
与人类用户的普通聊天、知识问答和单次代码解释不因此启动完整交付流程。
M 与 D 之间的任务协作仍须按 §6 使用模板，不因消息简短或属于技术讨论而例外。

## 2. 目标与基本原则

- 目标对齐：设计和实现均检查任务、阶段及项目整体目标；局部验收不能代替整体合理性。
  目标或已批准架构冲突时，带证据、影响和选项请用户决定，不自行扩大任务。
- 奥卡姆剃刀：在满足真实需求、项目约束与验收质量的可行方案中，优先选择职责清晰、
  概念、状态和依赖更少的最小充分方案。新增抽象、Package、配置、缓存或兼容路径时，
  说明现有机制为何不足及真实用途；不为未知未来需求预建能力，也不以简化为由删减
  必要校验、失败语义、生命周期保障或验证。
- 项目接入：通过适用的 `AGENTS.md` 链接地图读取权威计划、需求、架构和工程规范，不另建适配体系。
- 状态权威：分工、进度和交接沿用项目任务记录，不写入 Skill 或作为日志写入 `AGENTS.md`。
- 执行自主：M 把关目标、验收与接续边界，D 自主安排获准任务内的方案、顺序和验证。
  评审要求不等于操作清单，具体决定边界见协作协议 §3。
- 交付终点：获准完成的代码修改任务，默认提交并合入正确目标分支；任务完成后清理对应临时工作树和分支。
  明确的不提交、远端交付或保留要求优先，具体完成语义见协作协议 §8。
- 授权边界：保留他人改动，遵守实际权限与工具限制；Skill 不扩大任务或绕过用户指定停止点。
  已约定的正常交付连续推进，不额外增加确认门；远端操作仍须明确授权。

## 3. 角色与渐进加载

默认只有两个 AI 职责类型：

- 主控：简称 M，内部标识 `lead`，英文可称 Delivery Lead、Leader 或 Master。
  负责协调、设计与实现评审，并向用户报告。
- 执行者：简称 D，内部标识 `implementer`，英文可称 Implementer 或 Developer。
  负责设计、实施、自验和交付，直接向 M 报告。

M 兼任协调者和评审者，不默认增加常驻评审角色。
如确需独立评审，按主控规则和实际授权处理；
不能仅换一个角色名称，就把自己产出的成果称为独立评审。

本节是职责类型及别名的定义入口；M／D 不是具体人员的身份或消息地址。
D 默认由用户可查看、直接对话并持续接续的独立会话承载；
仅在用户明确选择后台子代理时采用该方式。创建与可访问性核验见主控流程 §3。
具体参与者的命名、身份关联与接续统一见
[协作协议 §1](references/collaboration.md#1-参与者身份)，任务归属与换人授权亦依该协议。

接续协作先读共享协议，再按当前职责和阶段加载；不预读另一角色的行为细节。
链接用于按需定位，不表示递归读遍全部文件。同一参与者兼任时按当前职责加载。
以下路径均相对于本 Skill 目录：

| 当前需要 | 资源路径 | 加载条件 |
| --- | --- | --- |
| 主控工作 | [主控流程](references/lead.md) | 协调、创建 D 或进入评审阶段时 |
| 执行者工作 | [执行者流程](references/implementer.md) | 设计、实施及生成验证产物时 |
| 协作与交接 | [协作协议](references/collaboration.md) | M／D 接续协作时共同读取 |
| 文档工作 | [文档规范](references/documents.md) | 编辑、修订、评审文档或引用证据时 |
| 提交前整理 | [收尾规范](references/pre-merge.md) | D 收尾整理及检查版本库纳入范围时 |

M 进入评审阶段时，由主控流程路由到设计评审或实现评审规范，
只加载当前阶段所需细节，不预加载两份规范；不按文档或代码扩展名选择阶段。

创建 D 的操作只在 [主控流程 §3](references/lead.md#3-复用或创建-d并完成首次派工) 展开，
首次派工使用 [feedback 模板](assets/lead-feedback.md#3-创建与首次派工)。

## 4. 共享流程

~~~mermaid
flowchart TD
    Scope["明确任务与授权"] --> Design["D 设计"]
    Design --> DR{"M 设计评审"}
    DR -->|修订| Design
    DR -->|通过，仅交付设计| Polish["D 提交前整理与自验"]
    DR -->|通过，按实施授权推进| Code["D 实施与验证"]
    Code --> IR{"M 实现评审"}
    IR -->|修订| Code
    IR -->|通过| Polish
    Polish --> Merge["按授权 rebase／squash 到目标分支"]
    Merge --> Handoff["必要保留、默认清理临时工作树／分支、最终交接"]
~~~

- 阶段接续：不重做未受影响的已完成工作；只做评审或查询时交付相应结论，不启动后续阶段。
- 评审修订：未通过则由 D 修订并重新交接，不提前变成“等待用户了解”。
- 实际暂停：用户指定的停止点或缺少必要许可时，按协作协议暂停受影响范围；不沿图默认取得权限。
- 收尾：保持已审行为与契约的 refactor、自验后，按约定直接合入和清理，不增加 M 增量确认。

## 5. 协作协议与文档范式

- 协作协议：统一归属、授权、交接、暂停／恢复和结束规则；角色文件只细化各自执行方式。
- 文档规范：统一 Markdown 分工、目录／命名建议、按文档用途选择表达及引用维护；项目已有约定优先。
- 维护时机：内容、契约和状态随工作更新；Markdown lint 等纯格式整理集中到提交前阶段。

## 6. Report 与 Feedback

M 与 D 之间所有协作消息必须按方向使用模板，包括技术讨论、澄清、方案补充和进展交流。
只有与人类用户的普通聊天不强制套用；向用户报告接手、进展、评审、交付或请求任务决策时
仍使用报告模板。报告开头标注具体名称与角色，简短状态查询也不能省略身份。
简短协作消息也保留共同消息头，按当前用途补充必要内容，具体要求见协作协议 §4。
只加载当前需要的模板。报告先说明整项状态、本轮结论、问题／剩余项和下一步，
再补用途所需的关键事实，版本与证据放在末尾；不重复完整材料或日志。
模板不新增报告频次、暂停门或状态台账，仍按协作协议接续已授权工作。

| 方向 | 类型 | 模板路径 |
| --- | --- | --- |
| M 向用户 | report | [lead-report.md](assets/lead-report.md) |
| D 向 M | report | [implementer-report.md](assets/implementer-report.md) |
| M 向 D | feedback | [lead-feedback.md](assets/lead-feedback.md) |

结论须能追溯到被审对象；面向用户解释 user case，面向执行者明确评审要求及必要接续边界。
面向用户的成果报告以可检查实体及实际变化为主，按
[实体与用例规则](assets/lead-report.md#41-实体与用例)关联设计、资产、实现和验证。
交接语义由协作协议定义，模板只组织消息，不另立流程或授权规则。

## 7. 效率约束与条件触发

- 日常原则：批量交接、按需读取、复用有效产物与证据、按变更影响验证，不降低必要质量保障。
- 专项改进：仅按 [协作协议 §9](references/collaboration.md#9-效率问题的识别与改进) 的条件触发，
  不随每份 report 或每个任务启动；D 提供已有事实，M 协调并检查效果。
