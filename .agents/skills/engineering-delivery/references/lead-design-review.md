# Lead Design Review

本文是 M 的设计评审规范，仅在方案交接或设计变更复审时加载，不要求 D 阅读。
共同判断依据、结论及后续推进见 [主控流程](lead.md#4-评审阶段与按需加载)，
授权和交接以 [协作协议](collaboration.md) 为准；不另建一套工作流程。

本文件审设计内容，不按文档扩展名判断任务类型。
只交付方案的任务按约定评审和收尾，不强加编码或重复的实现评审。
需要审代码、数据、工具或配套文档的实际交付时，再由主控流程路由到实现评审。

## 1. 对象、材料和判断范围

读取 D 的设计 report、候选方案、关键事实及相关权威要求，
核实被审版本、任务范围、前置依赖及待决事项。
不为凑齐模板字段退回合理的简洁设计，也不能用只有目标口号的计划批准编码。
按方案可能影响的行为和消费者确定检查深度，未涉及的维度不强行展开。

涉及文档时，将 [文档规范 §7](documents.md#7-修订与检查) 的内容判据纳入本轮设计评审，
不因方案技术上成立而省略对设计文档的判断。

修订轮次先接续未闭合问题和新变化，再核实相关前提；
已有明确结论且前提未变的范围不反复重审。
材料不足时指出缺少什么事实、为何影响判断，以及仍可独立推进的工作。

## 2. 目标、必要性和候选取舍

分别站在平台或公共能力提供方、实际应用消费者的角度审查，
并同时检查任务、阶段和整体目标是否一致。
分清真实产品需求、测试诊断、临时过渡和已批准的例外，
避免为消除一个应用的直接依赖就扩张公共 API，或把通用需求硬塞进应用特例。

比较适用的复用、不新增能力、私有实现或公共能力等候选，
用真实消费者、成本、约束和未来已知需求解释取舍，不为每项工作虚造多套方案。
判断是否是当前约束下的合理最优，而不是追求最大抽象或替未来未知需求预建框架。
如果任务目标本身与项目目标冲突，不能以方案完成局部验收为由放行。

## 3. 模块边界与契约

沿输入到消费者检查职责与依赖，确认低耦合和单一权威状态。
评估复用时，确认业务职责内聚、契约明确、依赖受控，能独立使用和验证；
代码相似或减少行数，本身不构成抽取公共模块的理由。
重点核对状态、资源、线程和生命周期所有权，
以及失败、取消、迟到结果、重入或跨版本数据是否有明确处理边界。
对公式和业务算法核实量、单位、来源、适用假设及调整方向，
不要仅凭经验常量或“以后可优化”认可缺少依据的策略。

需要公共接口、Schema、SDK 或其他共享契约时，
遵守项目正式设计流程，明确首批能力、消费者、版本和后续演进边界。
接口、实现、开发者文档和验收须相互对应；不能只凭内部调用能工作就宣称公开能力可用。
区分私有依赖、消费者直接依赖和公开契约泄漏，不把链接形式本身当作边界结论。

## 4. 验证与交付可行性

确认验收能对应真实 user case 和消费者，而不是只验证内部函数存在。
区分持久契约测试、稳定最小夹具和正式资产或真实环境 smoke，
选择能发现关键失败的窄测试，避免把会变动的产品数据写进大量无关单元测试。
需要跨实现、平台或安装态验证时，范围依据项目要求及实际影响确定。

检查独立交付出口、构建与运行前提、阶段冻结点及重要风险是否可落实。
无法实现的判据、遗漏的前置依赖或含糊完成语义先修订，
不能把设计问题留给编码期猜测，也不提前要求尚未分派的下游产品全部完成。

## 5. 结论与阶段交接

按主控流程给出绑定到版本及范围的结论和批量 feedback，
说明候选取舍、关键边界、验收安排和需要修订或补证的事项。
通过时向用户报告预期 user case、边界为何合理、如何验证以及限制，明确尚未实现。
具体推进或暂停由主控流程根据有效授权处理，不在本文件另增确认门。
