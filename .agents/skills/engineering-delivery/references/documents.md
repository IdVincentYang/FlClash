# Documents

M、D 开始文档编辑、修订或评审时读取本规范；角色及资源入口见 [Skill 入口](../SKILL.md)。
工程文档默认使用 UTF-8 Markdown（`.md`），采用 CommonMark／GFM 语法。
项目已有格式、目录、命名及文档职责约定优先，不要求新增全套文件。
内容归属、事实准确、单一权威及影响判断的范围与限制属于达标要求；
标作建议的目录、命名和章节骨架可以调整，不能因结构可选而省略必要信息。

## 1. 入口与权威关系

- 定位入口：通过项目 `AGENTS.md` 链接地图，查找当前目标、需求、架构及任务记录。
- 单一权威：同一需求、契约或状态有明确维护位置；其它文档引用，不复制平行清单。
- 当前与历史：长期文档维护需求、有效设计和用法，任务记录保存各次增量及证据。
  当前规范不依赖 Plan／Tasks／Result／Issue 才能解释规则；任务索引和验收管理入口
  可按职责链接记录，不充当产品规范。具体边界按项目 `AGENTS.md`。
- 按需建文档：已有位置能承载时直接修订；新增须有独立用途和可发现的入口。
- 链接代替搬运：引用相关章节，不复制大段规范、源码、日志或历史对话。

## 2. 文档分工、命名与目录

建议文件名使用稳定主题或任务标识、小写下划线及用途后缀，避免 `new`、`final_v2` 等临时命名。
专题根建议为 `docs/features/<feature>/`；每个阶段设 `<stage>/` 子目录。

| 用途 | 建议文件名 | 建议位置 | 内容边界 |
| --- | --- | --- | --- |
| 目录入口 | `README.md` | 所属目录 | 读者定位、阅读路径及必要索引 |
| 总 overview／索引 | `<feature>_overview.md` | 专题根 | 项目定位、模块关系及各模块入口 |
| 总计划 | `<feature>_plan.md` | 专题根 | 整体目标、阶段摘要、状态及阶段计划链接 |
| 模块 overview | `<module>_overview.md` | 专题根 | 全部业务需求、能力边界及实现覆盖 |
| 模块设计 | `<module>_design.md` | 模块旁或专题根 | 长期概要设计、关键决策及理由 |
| 阶段计划 | `<stage>_plan.md` | 阶段目录 | 本阶段用例、范围、需求、依赖及交付闭环 |
| 任务清单 | `<stage>_tasks.md` | 阶段目录 | 单层任务、负责人、依赖、验收出口和状态 |
| 任务设计 | `<task>_plan.md` | 所属阶段目录 | 本次问题、方案及理由、交付与验证；深度按影响确定 |
| 正式规范 | `<capability>_spec.md` | 所属专题或 `docs/specs/` | 正式语义、约束及演进规则 |
| 使用指南 | `<capability>_guide.md` | 所属专题或 `docs/development/` | 使用步骤与限制 |
| 问题记录 | `<topic>_issue.md` | 相关专题或阶段目录 | 问题事实、影响及关联修复任务 |
| 验证／交付记录 | `<task>_result.md` | 所属阶段目录 | 实际版本、配置、结果、限制和证据入口 |

- 按职责落位：稳定模块／契约资料不依附某次阶段；任务设计和结果随所属阶段组织。
- 按规模分目录：单个模块或任务资料确需继续细分时设子目录，由原入口链接；不为一份文件造多层目录。
- 架构位置：整体架构决策沿用项目架构目录，不混入某个应用任务的私有设计。
- 契约权威：声明、Schema 等已是正式源时，spec／guide 补充说明和链接，不另写冲突的接口定义。

## 3. 内容组织与轻量模板

- 技术术语：沿用[协作协议 §4](collaboration.md#4-report-与-feedback-的交接要求)的英文原名规则。
- 结论先行：开头说明文档对象、解决的问题或当前结论，再展开依据；状态和版本仅在有判断价值时列出。
- 按问题选表达：并列能力、验证发现和限制用列表；配置／结果、映射和对比用表格；
  流程、依赖或状态关系在图能明显降低理解成本时绘图。不因能画图就画图，也不要求每份 Result 有图。
  绘图规范见 §3.1。
- 列表组织：并列要求用短语列表，顺序操作用编号；必要推理用简短段落，不重复图中已表达的内容。
- 结构可导航：一个一级标题，按读者需要回答的问题设章节；用真实 Markdown 标题，不用加粗模拟层级。
- 表格有用途：用于对应关系、状态清单或候选对比，不将长篇方案和多行推理塞进单元格。
- 代码有边界：代码块标明语言，只保留解释契约或复现所需的最小片段；重复内容改为链接。
- 独立可读：正文描述需求和事实，不保留“你刚才说”“之前讨论过”等聊天口吻或失效上下文。

按以下读者问题组织和检查内容；它们不是必填章节或固定排列顺序。
正文、图表或精确引用可以共同回答，读者无需借助聊天记录补齐上下文。
按文档用途及实际范围取舍，不为不适用问题凑内容；影响判断的未知事实和未决事项须明确。

- 总 overview：项目定位和范围是什么？模块如何关联，具体能力与限制从哪里查？
- 总计划：整体目标是什么？各阶段目标、状态和计划入口在哪里，跨阶段依赖是什么？
- 模块 overview：服务哪些用户场景，现有能力、职责边界及使用／验证入口是什么？
  需求跟踪遵守项目约定，当前实现、未实现需求和限制是否区分清楚，依据在哪里？
- 阶段计划：本阶段形成什么可体验闭环？范围、需求、依赖、排除项及退出条件是什么，任务在哪里？
- tasks：每项任务的目标、M／D、依赖、设计入口、验收出口和状态是否可判断，是否保持单层拆解？
- 任务 plan：能否按 §3.2 判断任务必要性、方案成立的依据，以及如何交付并证明完成？
- spec：哪个对象和版本的正式语义由何处定义，约束、失败及演进规则是什么？
- guide：何时使用、怎样使用、需要什么前提，成功／失败如何观察，限制和参考入口在哪里？
- issue：预期与实际差在哪里，如何复现、证据与影响是什么？原因哪些已确认，处理目标和任务在哪里？
- result：本次实际证明了什么、哪些尚未证明？受测对象、条件、结果与偏差是什么，如何体验或复现？

Result 优先回答“实际证明了什么、哪些尚未证明、怎样复现”。保留支持结论的观察和
必要版本绑定；接口设计、内部调用链及实现理由链接 Plan／规范，使用步骤链接 Guide，
不重复完整设计、文件清单、原始日志或与判断无关的制品明细。
矩阵明确配置、结果及计数口径；失败、跳过、未执行和限制不能被压缩成笼统的“通过”。

### 3.1. 文档绘图

- 统一格式：文档图统一使用 Mermaid；默认内联于 Markdown 的 `mermaid` 围栏代码块。
- 图型选择：模块依赖／数据流用流程图，多方调用／异步交互用时序图，生命周期用状态图。
- 语法选择：采用目标阅读环境已支持的 Mermaid 语法。
- 按需查阅：[Mermaid 官方文档](https://mermaid.js.org/intro/)；嵌入语法见
  [GitHub 的绘图说明](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)。
- 表达范围：一图回答一个关键问题，节点名称与正文一致；大图按职责或流程拆分并保留关联。
  箭头注明调用、数据、依赖或先后等含义；涉及所有权、边界、条件或单位时明确标示。
- 列表补充：图后用列表说明条件、理由、限制及结论，不逐节点或逐箭头再写同义段落。
  区分当前实现与候选方案；图与补充列表共同表达同一份说明，不另建契约权威。
  Result 的图只汇总已观察的相关路径，不借验证示意图补充或重定义产品契约。
- 可读性：用明确标注区分语义，减少交叉连线。
- 源文件位置：默认内联；确需独立 Mermaid 文件时就近放置，如 `diagrams/<topic>.mmd`。
  正文用相对链接关联；每图保留一份维护源。
- 同步维护：行为、边界或名称改变时同步受影响当前文档的图与补充列表；历史图按 §5 保留。
  正式图源可随文档入库，临时预览／截图按协作协议 §8 管理。
- 检查范围：Mermaid 图仅做静态文本检查，核对代码围栏、图型语法、节点与连线、条件、
  标注及引用，并检查其与正文中的流程、状态、线程及所有权是否一致。
  不为检查启动渲染器，也不导出 SVG、PNG 或截图。
  Markdown lint 与静态检查均不能证明渲染效果，不声称布局或预览已验证。
- 本地处理：使用已授权工具；未经用户授权，不把本地图源或项目内容发送到在线编辑／渲染服务。

### 3.2. 任务方案

任务方案使用 [Task Plan 模板](../assets/task-plan.md)，围绕问题与目标、方案与理由、
实施与验证组织正文。已有位置能够承载时直接修订，小任务可合并为几段说明；
章节可按读者需要调整，关键答案仍须充分。已审或已完成记录不为套用新模板重写。

- 篇幅预算：普通任务方案以一页左右、约 500–1000 中文字为目标，作为压缩检查的软预算，
  不作为放行门槛。复杂设计保留理解和实施所需的信息，不以字数删减必要边界与推理。
- 内容取舍：每段须支持问题判断、方案选择、可行性或验证。根因、兼容、迁移等按实际
  影响融入相关位置，不为不适用领域设空栏或虚造候选；重要未知须说明其影响及解除方式。
- 控制增长：超出预算时，先删重复、引用已有权威、移出日志与机械清单，再核查是否混入
  独立任务。同一事实只解释一次，图表与正文互补；不得把必要正文搬入附件以规避精简。
- 分工边界：Plan 解释本次增量及决定依据；Tasks 管理归属和状态，长期 Design／Spec
  维护有效契约，Result 记录实际证据，Report 摘要交接并链接方案，不各写一套正文。

## 4. 计划与任务拆解

- 目标对齐：每项工作可追溯到阶段目标和业务需求；未覆盖需求明确落点，不遗漏也不重复承诺。
- 单层清单：同一任务清单维持一个拆解层级，避免阶段、任务、子任务混排。
- 后续细拆：某项已成为独立范围且需要继续拆解时，另设其任务文档，由父项链接。
  原层仍在规划时可直接修订，不为调整当前粒度绕行新增文档。
- 适时细化：未来阶段保留目标、能力、依赖和验收方向，不在关键前提未知时预排详细任务。
- 合理出口：按可验证、可提交成果划分，不按文件或函数造任务；依赖变化同步调整原记录。
- 所属关系：任务清单细化对应计划；不夹带无关工作或已失去上下文的聊天描述。
- 文档影响：Plan 列出本任务拟新增、修改、删除或迁移的具体文档路径、内容职责及交付顺序；
  包含相关需求、架构、契约声明／注释、开发者说明和索引。可沿用既有来源，
  不为凑齐类别创建文档，也不把实施后的实际文件清单复制成平行记录。
  先从当前规范确定增量；方案未定时不提前扩散修改，也不要求翻遍旧任务才能开始。
- 文档先行：方案确认后，先完成受影响的需求、架构、契约及开发者说明的文档基线，
  再编写生产实现与相应测试。M 在既有设计评审中核对该基线，不另增用户确认门。
  实施发现设计缺口时先修订相应文档，再按有效授权修改代码和测试。
  尚未实现的开发者说明必须明确标为 draft／未可用，不把预期写成现状；
  实际验证、覆盖状态和 Result 只在相应实现与验证后回填。

## 5. 需求、方案与实现同步

- 事实分层：区分真实需求、已批准决策、候选建议、当前实现及待核实事项。
- 状态有依据：使用项目既有完成语义，区分设计通过、实现通过、合入和结束；规则见协作协议 §6。
- 需求状态：Overview 的状态表达所承载业务需求的确认及交付进展，不评价文档质量。
  阶段及转换条件按项目规范维护；设计、实现和验证可交织推进，不要求先完成整体
  设计再进入实现。按完整有效需求及规定验收范围判断，不由完成子集推导整体完成；
  文字或格式修订、Review 通过和合入本身不升级需求状态。
- 覆盖可追溯：模块需求关联实现／验证依据和所属阶段，不以完成任务数代替业务能力完成度。
- 原实现参考：在相关模块或设计处链接旧项目资料，注明版本、章节和适用范围。
  参考材料不是现项目的权威契约；保留差异、取舍及尚未核实的部分。
- 及时同步：行为、契约、范围或依赖改变时更新相关说明，不把语义修订推迟到格式整理。
- 长期内容：将持久决定及理由维护到 Design、Spec、架构或声明，不整篇复制 Plan。
  长期文档区分当前实现、已批准但未实现及未决部分，Guide 不把目标写成可用保证。
- 完成冻结：任务交付合入后，其 Plan、Result 和 Tasks 中的完成事实在 Git 历史保留当时内容；仍有活动项
  的清单／阶段计划继续维护活动范围。后续变化由新任务及当前规范承担，不追改旧术语、
  路径、图或结论。事实错误可明确勘误，Issue 可更新处置行，必要时仅补一行接续指针。
- 版本绑定：在任务既有记录一处注明输入 Git 基线，Result 绑定实际受测提交或变更快照；
  它们不自动等于文档冻结版本。历史引用默认按任务文档冻结版本查阅，通过交付记录与
  Git 历史定位；引用其他版本时明确绑定。共用对象只记一次，不复制提交清单，
  可用 `git show <revision>:<path>`；缺基线旧记录按需核实，不批量回填或逐链接加 Hash。
- 合入后清理：D 将任务定稿合入目标分支后，M 按[主控收尾 §7.1](lead.md#71-合入后的任务文档清理)
  先据实际结果复核并 amend 交付提交的 Details，再独立提交任务文档清理。
  长期内容已提炼、未决事项已有归属、当前引用已处理且定稿可从
  目标分支历史取回时，删除已结束的 Plan／Tasks／Result；共享活动文档及必要证据保留。
  默认不另建归档目录或跳转页，不把清理并回交付提交。

## 6. 引用关系与维护边界

README 按层级提供导航；正文按事实归属引用权威；变更按真实影响维护；历史按版本追溯。
导航帮助读者找到内容，规范依据说明规则由何处定义；两者用途不同，目录深度不决定权威。

- **导航分层**：总 README 链接专题或目录索引，再由所属索引链接主题文档。
  直接所属的内部 Feature 索引可按项目约定展示 Overview 的需求状态及一句必要摘要，
  须来自所属 Overview 并随其同步，不独立评估。更上层入口继续提供导航，不复制
  下层设计、需求清单、逐平台矩阵或任务进度；对外入口按其目标读者取舍。
- **依据直达**：正文直接引用所使用事实的权威来源，例如 Guide 引用公开契约、Design
  引用需求与架构约束。必要的跨目录引用和相关阅读可保留，导航链接不构成规范依据。
- **单一维护**：每项事实只在所属文档定义；其他文档保留理解所需的摘要并链接来源，
  不复制独立演化的规则、状态表或易变实现细节。当前规范不经单项任务记录拼接当前规则。
- **按影响更新**：变更时定位权威来源及真实受影响的当前消费者和导航。
  仅有链接不意味着正文也须修改，不沿引用链递归回写；真实受影响的解释、示例和约束仍须同步。
  路径或章节迁移按项目规定扫描入站引用，核实目标语义，不能以减少改动为由漏掉当前消费者。
- **历史冻结**：任务记录按其基线保留当时设计、引用和结论，后续变化由新任务与当前规范承担。
  版本绑定及合入后清理见 §5，不要求历史文档持续追随实现。

证据交接及本地产物管理分别遵循[协作协议 §4](collaboration.md#4-report-与-feedback-的交接要求)
与[§8](collaboration.md#8-收尾合入与结束)，本节不重复其操作要求。

## 7. 文档质量与评审

文档编写与 Review 必须向 Google 技术文档的质量看齐，以

作者与 Reviewer 共用以下标准，目标是让读者准确理解主题，并获得文档承诺的知识或能力。

- **对读者有用**：围绕目标读者及其问题组织内容，补足理解或完成任务所需的信息。
  读者能够从正文获得关键答案，无需自行拼接源码、历史记录或聊天上下文。
- **准确可信**：技术事实、解释和示例符合权威契约及实际行为，范围与限制明确。
  清楚区分现状、已确认目标和未决事项，不能把推测或计划写成可用保证。
- **具体清楚**：说明关键概念、关系、过程及理由，用具体解释消除歧义。
  术语、职责表或约束清单须帮助理解，不能替代必要解释。
- **简洁聚焦**：每段服务于阅读目标，删除重复、空泛和无关内容。
  深度以正确理解所需为准，精简时保留必要的前提、边界和推理。
- **组织易读**：结构符合读者的理解顺序，重点突出、术语一致、信息易于查找。
  按表达需要使用文字、示例、表格和图，具体方法见 §3，不机械套用章节模板。

D 交评前按这些标准自查，M 在已有设计／实现 Review 中审查实际正文，并核对关键技术依据。
内容质量达标是放行条件；约束对账、格式和链接检查只是基础检查，不能作为质量通过的证明。
不达标的内容须修订后再评审，不能留到提交前格式整理。符合标准的组织与表达由作者自主选择。
问题沿用现有 report／feedback 交接，不另建合规报告或增加评审门。
