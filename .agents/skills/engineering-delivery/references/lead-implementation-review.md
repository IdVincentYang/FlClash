# Lead Implementation Review

本文是 M 的实现评审规范，在实际成果交接或受影响实现复审时加载，不要求 D 阅读。
共同判断依据、结论及后续推进见 [主控流程](lead.md#4-评审阶段与按需加载)，
授权和交接以 [协作协议](collaboration.md) 为准；不另建一套工作流程。

实现成果可包括代码、数据、工具及配套文档，不只按代码文件划定检查范围。
只有设计交付时，按其任务约定使用设计评审，不强加不存在的编码或验证要求。
仅需核验构建证据时可只读取 §3，不因此重新启动完整实现评审。

## 1. 变更范围与设计落实

核对被审源码或成果基线、完整变更范围及其与已批准设计的差异。
读取实际实现和必要调用链，不只对账 D 的总结或测试通过数量。
后续轮次重点审新增修改及其影响，同时保留未闭合问题；
不因沿用旧结论而漏掉已改变的前提，也不重复审未变且仍有效的范围。

核实公共契约、生成结果、依赖和实际消费者是否有同步变更，
区分本次引入、既有问题及未覆盖范围，不把无关改动混入本次完成声明。
只有文档或数据的交付仍审其语义、权威关系和消费者，
不因没有运行代码就免除关键验收，也不要求不适用的构建和运行矩阵。

## 2. 正确性、边界与可维护性

分别从公共能力和应用消费角度检查，深度与项目要求及变更影响相称：

- 目标与契约：实际能力符合任务、阶段和项目目标；没有未审的范围或公共契约变化。
- 正确性与所有权：状态转移、资源释放、线程协作和失败路径完整，单一权威不被副本覆盖。
- 边界与复用：复用以高内聚、低耦合的模块边界为前提，不以机械抽取代码替代职责划分。
  模块依赖合理；无重复实现、无效缓存或层层重复防御。
  外部信任边界保留必要校验，不能用静默兜底掩盖内部不变量损坏。
- 可维护性：接口契约和非显然实现的原因／约束有必要说明；
  非平凡公式和项目算法解释来源、单位、理由、假设、当前状态及调整方向。
  注释随行为更新，契约说明不维护重复权威；语言和形式遵守项目规则，不给自明代码套模板。
- 消费与证据：真实消费者走到本次生产路径；测试有独立预期，准确报告失败、跳过和未覆盖项。
  夹具、替代后端或源码树内调用不能冒充正式安装态、实际后端或完整产品能力。
- 文档与状态：契约和使用说明与实现一致，完成范围没有扩大；
  按 [文档规范 §7](documents.md#7-修订与检查) 判断实际文档是否达标，纳入本轮实现评审。
  格式 lint 和行为不变的提交前整理留给收尾，不代替此处的语义与代码质量判断。

## 3. 产物绑定与必要复核

依据协作协议 §4 的复用政策，检查产物与被审范围的对应关系：

1. 核实源码提交或变更快照、构建配置、平台、依赖状态及使用命令。
2. 检查必要校验值或清单，确认现有产物正是 report 指向的对象。
3. 对照实际测试范围、结果、运行前提及未覆盖项，判断能支持哪些验收。
4. 对源码推理仍有疑点或用户要求独立验收的范围，选择最小必要复核。

已绑定的构建及机械检查不默认重跑。复验优先运行 D 已生成的产物，
不改写冻结证据；运行输出按项目规则放在独立的临时或忽略位置。
只检查足以识别本次对象的校验信息，不为每次小交接重新生成全套产物清单。
目标分支名称或提交历史变化不自动使产物失效，
但需核实源码、配置及集成条件是否仍等价，不能用同一文件名推断等价。

出现源码与产物不对应、配置缺失、结果矛盾或疑似缺陷时，
一次向 D 说明缺口和最小补证目标，优先由负责该构建的 D 修复或重新生成。
新变更使旧证据失效时，只更新实际受影响范围；
必要全量或多平台验证依项目验收要求安排，不由局部疑点任意扩大。
生成责任例外或复核需要新权限时，按协作协议处理，不自行接管构建或扩大操作。

## 4. 问题证实与修订反馈

发现问题时给出位置、触发条件或完整推理、影响，以及对应要求或技术依据。
按主控流程分类、汇总和下发 feedback，区分已证实缺陷与尚需澄清的疑点。
影响关键验收的证据缺失或疑点不能作为“非阻塞讨论”绕过；
明确哪些结论未作出，哪些独立工作仍可继续。

设计本身有问题时，只对受影响方案加载 [设计评审](lead-design-review.md) 并复审，
不要求 D 为遵守旧处方继续错误实现，也不因此重做所有未变设计。

## 5. 结论与交付衔接

结论对应实际版本、配置、范围和有效证据，不把局部测试通过等同于完整交付。
通过后向用户解释已实现的 user case、直接体验入口、运行前提及限制。
提交前整理、合入、清理及交付对账回到主控流程和协作协议处理，
不新增 M 增量确认或第三道评审门。
