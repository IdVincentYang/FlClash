# Pre-Merge

D 在 M 对本任务约定成果评审通过后加载本规范；只交付设计的任务也按其约定收尾。
授权、产物保留和结束语义以 [协作协议 §8](collaboration.md#8-收尾合入与结束) 为准，
文档整理使用 [文档规范](documents.md)。不涉及仓库变更时直接完成约定交接。

~~~mermaid
flowchart TD
    Passed["M 对约定成果评审通过"] --> Tidy["D 提交前整理"]
    Tidy --> Checks{"整理自验通过？"}
    Checks -->|否| Tidy
    Checks -->|是| Integrate["按交付约定 rebase／squash 与集成自验"]
    Integrate --> Ready{"集成自验通过？"}
    Ready -->|否| Integrate
    Ready -->|是| Merge["合入指定目标分支"]
    Merge --> Preserve["处理必要保留与复现入口"]
    Preserve --> Cleanup["任务完成后默认清理临时工作树／分支；例外则保留"]
    Cleanup --> Handoff["最终 report 与任务状态对账"]
~~~

- 正常收尾由 D 连续完成，不增加 M 增量确认或第三道评审门。
- 整理保持已审行为与契约；实质变化按 [D 问题处理](implementer.md#52-任务内无法解决的问题) 交接。
- 图示为默认本地交付；明确的不提交、远端交付或保留要求按协作协议 §8 调整。
  真实权限／目标冲突只暂停受影响步骤，不将已完成的整理重新交给 M 评审。

## 1. 起点与整理边界

- 已审基线：核实通过的提交或变更快照、评审范围及已接受的限制。
- 实际状态：核对工作树、分支、暂存及未跟踪文件，区分本任务成果和他人已有改动。
- 合入目标：核实约定目标分支、当前基线、交付例外及共享分支的集成责任，不重复请求已有许可。
- 整理范围：本任务内的行为不变 refactor、代码风格、注释、文档格式及版本库纳入检查。
  公共契约、状态／资源所有权及业务策略沿用已审方案；确需改变时回到相应任务流程。
- 工作依据：使用项目既有工具、配置和权威规则，复用已有效的检查结果。

## 2. 代码与文档整理

- 内部整理：统一命名和局部结构，清理无用分支、重复计算、无效缓存、临时包装／调试代码及重复说明。
  先核实调用、构建注册和验证用途；有意保留的产品能力或持久测试按原职责维护。
- 参数校验：沿调用链核实契约，删除上游已保证且当前内部路径不会失效的重复检查。
- 必要检查：保留外部输入、信任边界及可失效条件的校验；内部不变量损坏按项目失败机制处理，不静默兜底。
- 模块边界：在已审职责内整理，不因代码相似新建通用模块；复用前提见 [D 流程 §2](implementer.md#2-准备方案与设计交接)。
- 注释对齐：消除过时或重复说明，核对接口、实现及公式注释与代码一致；具体要求见 D 流程 §3。
- 代码风格：运行涉及语言的项目格式／静态检查入口，只处理本次及其受影响范围。
- Markdown lint：集中检查本任务涉及的手写 Markdown；按项目要求的范围与配置修复格式。
  语义和状态此前随任务维护，此处不以格式整理替代必要的内容修订。
- 引用与符号：核实变更涉及的路径、锚点、章节号、接口名及使用命令；移动或删除内容时检查入站引用。
  核实规范事实仍在唯一权威位置；方法见文档规范 §6。
- 图与列表：按文档规范 §3.1 核对变更的 Mermaid 图及补充列表，区分语法检查与实际预览结果。
- 检查基线：遵守项目的零违规或增量判据；继承问题单列来源和影响，不把净增通过写成全量通过。

## 3. 版本库纳入检查

- 完整清单：检查本任务新增、修改、删除、暂存及未跟踪文件，确认归属和必要性。
- 产物分类：核对二进制体积、文件用途及忽略状态，按协作协议 §8 判断是否应入库。
  必要产品资产／最小 golden 的例外依据须齐全；临时预览和可复现证据留在约定的忽略位置。
- 复现入口：保留必要的源输入、脚本或命令、配置和结果摘要；仅纳入项目规定需要随源同步的生成文件。
- 提交范围：逐项核对待提交差异，排除他人改动、私有配置和非交付产物；不以整理为由清空工作目录。

## 4. 按整理影响自验与绑定证据

- 差异核对：比较已审基线与整理后成果，确认每项变化属于整理范围，行为及契约保持一致。
- 纯格式／注释：运行相关格式、lint 和引用检查；没有代码行为变化时不默认重建或全量回归。
- 代码整理：构建受影响目标，运行能覆盖变更路径的测试；涉及构建、数据或部署时补相应消费者验证。
  必需矩阵按项目要求执行；具体选择方法见 [D 流程 §4](implementer.md#4-按变更影响自验与准备产物)。
- 失败处理：区分本次引入、继承问题和环境前提；任务内修复后更新受影响结果，未解决项明确交接。
- 证据复用：关联已审版本、整理后版本、实际配置、命令和输出摘要，注明哪些旧结果仍有效及理由。
  源码或集成条件改变时更新失效证据；只改提交历史不自动要求重新生成产物。
- 冻结记录：按文档规范 §5 保留已完成任务的原设计与证据，不为当前路径、术语或行为回写历史。
  本任务新增验证按实际对象另记；报告对账当前成果，不将旧矩阵改成新版本通过。

## 5. Rebase／Squash 与合入

- 更新基线：核实指定目标分支的最新实际提交和工作区状态，按已约定的集成顺序推进。
- 整理历史：在许可范围内 rebase 到目标基线、squash 为约定交付提交，保留任务的必要上下文。
- 解决冲突：由 D 处理已审边界内的普通冲突，核对双方变化及调用关系，保持既有行为和他人成果。
  需要实质设计变化或无法判断时，只交接受影响问题，不把普通冲突都变成用户确认门。
- 集成自验：检查 rebase 后差异及交叉影响，更新必要的格式、构建或测试证据。
  源码、配置和集成条件均等价时可复用产物，说明原构建版本与最终提交的对应关系。
- 提交信息：标题和正文均必填，遵守项目格式。正文用列表按重要性总结关键功能、契约、
  数据或文档的实际新增、修改、删除及结果；必要时说明原因、验证与限制。
  涉及模块或 API 的变更时，按项目提交规范说明职责、提供与消费关系及公开／内部边界，
  不以接口名称或文件清单代替协作说明。
  此要求同样适用于开发中的普通提交和合并提交；rebase／squash 后按最终差异整理，
  保留整个交付的关键总结，不把阶段结果写成整项完成。历史改写不改变任务身份。
- 目标推进：确认目标基线仍有效后，以已授权方式合入，核实目标分支的最终提交及实际文件内容。
  目标已变化时重新核对受影响范围；本地合入与远端发布分别依据有效授权处理。

## 6. 最终交接与清理

- 证据交接：清理会使路径失效时，先处理必要的保留位置或复现入口；按保留政策选择，不默认保存整套构建备份。
- 清理执行：临时 worktree 的任务合入 `main` 且完成后，默认清理对应工作树和 feature 分支。
  核实成果已交付、目标内无未交接／他人改动；明确保留或仍有进行中工作则保留并说明原因。
  只处理已核实的任务目标，不清主工作区、共享缓存或远端；核实目录、Git 登记和分支实际结果。
- 最终 report：使用 [最终交付模板](../assets/implementer-report.md#7-最终交付)，按协作协议 §4、§8 汇总一次完整交接。
  给出实际合入位置、最终版本、整理及自验结果、证据关联、体验入口、限制及清理／保留结果。
- 报告对账：完成和未改声明对应实际差异、检查结果或工具输出；通过数、失败数、跳过和未验证项分别说明。
- 任务状态：在既有记录中区分已审、已合入及已结束；向 M 交接后结束本次范围，后续工作依据新任务安排。
