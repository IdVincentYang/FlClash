# Lead Report

M 向用户的报告模板；交接规则见 [协作协议 §4](../references/collaboration.md#4-report-与-feedback-的交接要求)。
与人类用户的普通聊天不强制套用；接手、进展、评审、交付或请求任务决策时使用本模板。

## 1. 使用方式

- 顺序：每个任务的摘要 → 当前用途的必要要点 → 依据；不照填所有变体或空章节。
- 任务分隔：单任务使用 §2；多任务按 [§8](#8-多任务报告) 逐项成节，
  不共用混合的状态、问题、能力、验证或下一步，也不以开发者代替任务边界。
  用户询问某项成果时，只报告该项；前置任务就近引用，不展开其完成报告。
- 状态：沿用任务记录，写明整项状态和当前阶段；局部通过不等于整项完成。
  完成须符合协作协议 §8 的实际交付约定，不以 Review 通过代替必要的提交／合入。
- 问题：突出未决问题、剩余验收门及影响，区分真实阻塞与仍可推进的工作。
- 精简：用用户能理解的效果说明贡献；细节链接原文，不复述历史、完整评审或日志。
- 取舍：省略未发生的增删改、不适用分类和空字段；不以“没有删除”等文字填齐模板。
  影响理解的未覆盖范围、消费状态和真实限制仍须说明。
- 依据：实体与设计链接就近放在支撑的条目中；末尾补本次版本和必要证据。
  命令和校验遵守项目要求。
  不重复长清单、联系端点或已知运行环境；影响本次判断的信息仍须提供。

## 2. 共同消息头

报告开头先标注已确认的具体名称与角色。简短报告可以把主题和身份合并为一行：

~~~markdown
<M 的具体名称>（M）→ <用户>｜<任务标识／标题> · <用途>
~~~

随后保留本次必要的状态、问题、下一步和依据；不能用角色名或聊天标题隐含发送人。
下列完整消息头适用于需要展开的报告，身份同样放在开头：

~~~markdown
<M 的具体名称>（M）→ <用户>｜Report · <任务标识／标题> · <用途>

- 状态与结论：<整项状态、当前阶段；本轮评审或交付结论及适用范围>
- 问题与剩余项：<仅在有未闭合事项时说明其影响>
- 下一步：<有必要接续时说明；需用户决定或暂停时写明条件>

<按当前用途补充必要要点>

- 依据：<权威任务／设计／结果链接，本次版本及必要证据入口>
~~~

## 3. 设计评审通过

~~~markdown
- 预期用例：<用户能做什么、解决什么问题；明确尚未实现>
- 方案与边界：<关键取舍、涉及模块和职责；详细设计链接原文>
- 验收方式：<预期操作、可观察结果及必要前提>
~~~

仅交付设计的任务，最终报告沿用本变体并补实际文档版本与交付位置，不声称功能已实现。

## 4. 实现通过与最终交付

任务结束时，M 默认按可独立理解的成果逐项说明，让用户能直接了解和检查交付，
不只列模块名或完成结论。先交代整项状态，再使用下面的成果结构；细节按改动复杂度取舍，
简单成果可合成一句，复杂成果展开关键操作、行为与限制，不要求用户先追问才补成果链接。

~~~markdown
1. **<成果名称>**：<解决什么问题，具体新增／修改／删除什么>。
   <涉及模块／API 时，简述提供方与消费者、职责划分及理解协作所需的关键约束>。
   <如何使用或检查，关键行为与边界>；就近附[关键成果](<实际接口、指南、实现或制品链接>)。
   <重要用例的实际验证结论及未覆盖范围，必要时链接对应测试或证据>。
2. **<下一项成果>**：<按同样方式说明，省略不适用内容>。

- 交付：<amend Details 后的实际交付 SHA、独立清理提交或制品版本；合入／保留位置，必要时说明原受测版本的对应关系>。
- 工作树：<本任务使用的路径、分支／HEAD、clean／dirty 及未提交改动归属；保留／清理状态与原因>。
~~~

### 4.1 实体与用例

- 按实体列成果：围绕具体模块、接口／符号、资产／Schema、配置、构建 Target、
  测试用例或可运行制品，说明本次新增、删除或修改了什么以及用途。
  不以“增加集成验证”“完善流程”或测试总数代替交付内容；也不逐文件抄 diff。
- 说明职责与协作：模块／API 成果按[协作协议 §4](../references/collaboration.md#4-report-与-feedback-的交接要求)
  概述谁提供、谁消费、公开与内部如何分工；调用、数据或资源如何交接只展开本次必要部分。
  职责或契约变化说明前后差异，不用 API 名称堆列或完整 Reference 代替边界解释。
- 按视角分组：框架／应用类项目默认从用户、Framework、App 角度列相关模块变化，
  其他项目沿实际层级，用户指定方式优先。只展开有实质内容的分类；
  用户侧尚无新操作且影响交付边界理解时，说明需求归属、已交付子项和真实消费状态，
  不把既有体验重新计作新增，或把 App 接入写成 Framework 新公共能力。
- 给检查入口：每项成果的关键说明都就近附可点击链接，直接指向支撑该说明的公开契约、
  使用指南、实现／符号、测试或制品；按需要选择，不机械列齐每一类，也不逐文件堆链接。
  接口、调用顺序、参数、策略等解释展开到不同实体时，在对应段落分别给入口，
  不只在整段讲解末尾放总指南或 Result。必要时定位到已核实的行号／章节；
  对话中的本地文件使用绝对路径，仓库文档内的相对引用仍遵循文档规范。
- 对齐需求和设计：关键实体关联已有需求 ID、Spec／Schema 或批准设计的相关章节，
  说明它承担哪一部分，避免只有代码路径而无法对应业务目标。
  既有资产被新消费者使用时，列出实际资产入口及读取的关键值；
  区分既有输入、新增持久资产、运行时记录／资源及测试夹具，不混称资产类型。
- 给重要变化配用例：用实际输入或操作说明预期／观察到的结果，并指向相应实现、
  测试用例或制品；例如某资产字段如何变为接口输入、状态改变后查询读到什么。
  设计预期、工程夹具与正式玩家体验分别说明，机械格式修改不强配用例。
- 说明算法来源：移植或参考原项目的算法，按函数／计算说明原版对应位置、已核版本
  及本项目适配／推导部分；源码对应不等于原程序运行或逐位一致性已验证。
- 证据只支撑结论：列重要用例的实际检查结果及适用范围，详细矩阵就近链接。
  为写报告不另建资产目录、状态台账或来源清单，不补跑未受影响验证。
- 提交说明与报告一致：最终成果使用 M 在清理文档前复核 Details 时确认的同一组事实；
  报告链接源码与证据，交付提交的 Details 本身也须保留关键职责、行为和验证摘要。
- 交代工作树：最终报告核实并说明本任务实际使用的 worktree 路径、分支／HEAD、
  clean／dirty、未提交改动归属及保留／清理结果与原因。开发工作树与交付目标不同时分别说明，
  不把 feature 提交写成已合入目标分支；未创建独立 worktree 时报告实际开发目录，
  不为汇报新建工作树或罗列无关工作树。
- 按用户要求展开：最终报告后继续解释成果时沿用上述就近链接规则。用户要求逐项细讲时，
  按成果顺序展开当前项，保留关键操作、参数和边界的成果入口，不重复整份成果清单。

## 5. 需用户决定

~~~markdown
- 决策依据：<造成当前问题的关键事实，以及为何超出任务内决定权限>
- 选项：<推荐项及理由，其它可行项的收益与代价>
- 请求：<具体选择或新增权限；权限请求写明操作目标、内容和用途>
~~~

## 6. 状态查询

~~~markdown
- 关键进展：<最近实际交付或变化；不重复摘要中的状态、问题和下一步>
- 时间：<仅在需要时按已有记录区分执行、等待和日历跨度，不猜测耗时>
~~~

## 7. 局部改进交接

仅在已开展或未闭合的改进需要交接时附加；触发与频度见 [协作协议 §9](../references/collaboration.md#9-效率问题的识别与改进)。

~~~markdown
- 改进结果：<已证实问题、采用的措施、已有可比较结果或尚未验证；剩余事项>
~~~

## 8. 多任务报告

一条消息可以报告多个任务，共同主题和发送／接收信息只写一次。
每个任务分别使用 §2 的摘要字段，并按其当前用途补 §3–7 的必要要点与依据；
同一开发者的不同任务也分别列出，不把一项的评审、验证或交付结论归给另一项。
只列本次相关的任务，不为凑齐清单重复已交接且未变化的任务。
跨任务依赖就近说明涉及的任务；确需共用说明时放在各任务之后，不替代逐项结论。

~~~markdown
<M 的具体名称>（M）→ <用户>｜Report · 本轮任务进展 · <用途>

## <任务标识／标题>

- 状态与结论：<此任务的整项状态、当前阶段及本轮结论>
- 问题与剩余项：<仅在此任务有未闭合事项时说明其影响>
- 下一步：<此任务有必要接续时说明；需要用户决定或暂停时说明条件>

<此任务按 §3–7 补必要要点，例如实际能力、体验、验证与交付>

- 依据：<此任务的权威入口、本次版本及必要证据>

<逐项重复上述任务章节；共同发送信息不重复>
~~~

## 9. 启动说明

按 [Skill 入口 §1](../SKILL.md#1-用途与触发)及
[协作协议 §1](../references/collaboration.md#1-参与者身份)确定使用说明与身份。
启动开场可用一两句自然语言，将已核实的身份、任务和阶段合并说明，无需另发完整 Report。
下面只示例信息组织，不预设参与者名称或任务归属；D 使用时改为自己的角色及交评对象。

> 本次使用 Engineering Delivery。我是已确认的主控〈名称〉，负责〈任务〉；
> 当前处于〈阶段〉，由〈D 的具体名称〉向我交评。

身份尚未确定时，说明待确认项并按协作协议处理，不套用已确认身份的表述。
