# 应用分流与三种模式 Plan

本方案已获用户批准，05／06 已交付，覆盖 [05–07](network_activity_tasks.md#na-t01-05-应用接管控制闭环)
的控制关系、交互及实施边界。输入基线为 5a7704d；05／06 本次连贯交付；07 的 Host 例外另行实现。
总 Plan 与 Tasks 已同步本轮批准的模式和交付边界。

目标是保留 Global 的全局代理含义，让应用策略在 Rule、Direct 下生效；
用户选择 Direct 后，只需打开少数应用的单独策略，就能让它们代理、其余应用直连。
不增加第四种模式，不把三个模式改称默认路由。

## 1. 控制关系

Start／Stop 决定 VPN 是否运行。停止时所有策略只能保存，不能由 FlClash 转发应用流量。
Access control 决定哪些应用进入 VPN；本方案的分流只作用于已进入 VPN 的连接。
它继续作为接管范围的唯一设置来源，不能再建一份接管名单。

应用策略是本地的分流设置，不是第二次接管，也不是 VPN 开关。新增策略默认关闭，
因此升级后没有应用例外，原有出口选择不变。订阅、DNS 和来源准备继续沿现有实现，
本次只叠加应用策略，不增加独立的订阅隔离机制。
以下均指进入 VPN 的新业务连接，表中的应用策略已启用且没有更具体的本地 Host 例外。

| 应用策略 | Rule | Global | Direct |
| --- | --- | --- | --- |
| 关闭应用规则 | 依原有规则分流 | 使用 GLOBAL 组当前选择 | 直连 |
| 默认直连 | 直连 | 使用 GLOBAL 组当前选择 | 直连 |
| 默认拒绝（REJECT） | 拒绝连接 | 使用 GLOBAL 组当前选择 | 拒绝连接 |
| 默认使用指定组／节点 | 使用指定目标 | 使用 GLOBAL 组当前选择 | 使用指定目标 |

Global 忽略应用默认策略、应用 Host 例外及其它分流规则；设置保留，切回 Rule／Direct
后恢复参与匹配。GLOBAL 组的选择仍由 Proxies 管理，不被应用设置改写。
Direct 表示直连模式，允许明确启用的应用例外；界面显示“Direct · N 个应用例外”，
不能在存在例外时声称所有应用均直连。N 只统计已采用配置中启用的应用策略。

## 2. 匹配顺序与 Host 规则

Rule 的顺序为：本 App＋Host 例外 → 本地的跨 App Host 规则 → 本 App 默认策略
→ 原订阅及原有手工规则。相同作用域的重复设置更新原项，不堆积重复规则。
订阅中声明的应用规则仍属于原订阅规则，不能覆盖本地应用策略。

Direct 的顺序为：本 App＋Host 例外 → 本 App 默认策略 → DIRECT。
订阅规则、原有通用手工规则和跨 App Host 规则均不参与，避免未启用应用因某条域名规则走代理。
本 App＋Host 例外和默认策略共用该应用的启用开关；关闭后两者一起暂停，内容仍保留。
这也为任务 07 保留了 App A、App B 访问同一 Host 使用不同出口的能力。

不提供独立的“跟随模式”选择；关闭应用规则即恢复模式路径，保留原配置供下次启用。
07 允许只配置 Host 例外而不配置整个 App 的默认动作；这时未命中例外的连接继续模式路径，
关闭开关则暂停这些例外。它是规则未命中的自然行为，不增加一个同义的策略按钮；空规则不保存。
本地应用默认策略同样允许被更具体的本地 Host 设置覆盖，页面不能把它当作所有连接的唯一出口。

## 3. 入口与控件

入口沿用 Tools → 应用网络。页面读取现有模式，仅提供必要的只读状态，不新增模式切换控件。
切换 Rule／Global／Direct 仍使用 Dashboard 既有 outbound mode；其布局、交互和逻辑均不改。
列表名称、连接数、最近活动和原点击导航保持现有布局。

### 3.1. 应用代策略开关组件

每个已知应用的 item 右侧为一个独立窄列：上方显示策略／组／节点名称，下方为启用应用规则的开关。
开关点击立即保存并请求采用，不增加 Save 按钮；点击 item 主体仍进入该 App 的目标列表。
上方名称是独立可点击入口，不扩大开关的点击范围，避免查看名称时意外启停。

该上下布局统一命名为“应用代策略开关组件”。优先让组件与左侧图标、中间信息区协调，
不预先固定只能一行：按中间信息区的高度预算使用一或两行名称，仍超长才省略。
标题上沿至开关可见下沿的总高度应小于等于中间信息区高度，组件整体在该区域内对齐。
可见高度预算不以缩小触控区域或压小字体实现；大字体时整行统一适应，不裁掉文字或开关。
右列宽度受可用空间约束，不挤占应用名称和连接摘要。完整名称、类型与所属订阅在选择页显示，
长按／桌面悬停也可查看；不使用跑马灯。小型图标区分组与节点。
选择分组时显示组名，不随组内自动选点而改成成员名；直接指定节点才显示节点名。
右上方显示保存的策略目标，原连接出口摘要继续表示观察事实；二者不能冒充同一种信息。
关闭时摘要显示跟随规则／直连，上次单独目标保留在选择页中；Global 暂停或 VPN 未启动时，
已开启项仍保留原目标并附相应状态，避免误以为设置丢失。

### 3.2. 独立的应用策略选择页

点击右上方策略名称，直接进入全屏“应用策略 · App 名称”选择页，避免从上半屏操作后转向底部面板。
页面复制 Proxies 的选择布局和卡片视觉样式，新增独立页面及所需展示代码；
原 Proxies 选点页面、卡片和选择逻辑不改，不抽取共用选择组件，不增加原页的临时选择模式。
Group management 仅按第 6 节补充分组可用状态提示，不改原 Proxies 的选点布局与行为。
可沿用项目通用的基础控件及只读目标数据，应用策略的选择状态、搜索状态和提交行为独立持有。
卡片点选只返回本 App 的策略目标，不引入原页的 changeProxyDebounce、selectedMap 修改或连接重置行为。
这里有意复制展示布局，不通过改造原 ProxyCard 或 ProxiesView 来实现共用。

顶部显示当前 App、订阅和只读模式。其下固定提供“直连 DIRECT、拒绝 REJECT”常用策略；
公共应用组作为一个明确的目标选项。下方是顶部搜索框、全部／分组／节点筛选以及 Proxies 风格的卡片列表。
搜索使用既有匹配语义查找组／节点名称和类型，不改原 Proxies 页的搜索词、滚动位置或选中分组。
常用策略不因搜索而消失；空结果可清空搜索，不用层叠下拉框。

点击分组卡片选择整个组；独立的“查看成员”入口可以浏览成员，点击成员则直接选择该节点。
选择组意味着沿用该组当前选择与自动策略，不复制分组或修改其当前成员。完整名称允许换行，
选中标记对应此 App 当前配置，不对应 GLOBAL 或订阅 Selector 的选中状态。

完成一次目标选择后保存并返回；本地保存失败留在选择页并保留选择，运行配置采用在应用列表继续反馈。
普通编辑保留原开关状态：关闭时改目标只预设，不暗中开启；首次开启缺少目标时完成选择才启用。
App 目标列表页也可进入这个选择页；07 的多条 Host 规则管理保留独立列表。

| 控件／动作 | 行为 |
| --- | --- |
| 关闭开关 | 暂停该 App 的全部单独策略；Rule 跟随原规则，Direct 直连 |
| 首次打开开关 | 使用已选的公共应用代理组；没有可用目标时进入选择页，返回取消不改变开关 |
| 再次打开开关 | 恢复该 App 上次保存的策略和 Host 例外 |
| 点击右上方名称 | 打开独立选择页；即使 Global 或 VPN 未启动也能编辑预设 |
| 右上角菜单 → 应用代理组 | 为尚未指定独立分组的应用选择公共代理组；使用独立组的应用不受影响 |
| 右上角菜单 → VPN 应用范围 | 进入已有 Access control；不把应用策略开关兼作接管开关 |

公共应用代理组只需选择一次；每个 App 可以显式覆盖它。修改公共组须在选择页显示受影响应用数量，
确认后保存。分组直接作为路由目标，不要求先加入订阅的“默认节点”，也不切换该组的当前成员。
任务 06 交付前不提前放置无效的应用策略控件；任务 05 的逐应用接管入口放在 App 页面菜单中。

### 3.3. Global 与开关状态

顶部提示指第一层“应用网络”的 App 列表页；在其模式位置持续显示“Global · 应用规则暂停”。
新应用策略选择页的只读模式栏也显示暂停，说明这里只保存预设。此处“保留开关位置”
仅指每个 App 右侧的应用代策略开关组件，不是 Global 开关；Dashboard outbound mode 控件不改。
保存为开的开关保持右侧位置，以等待色和暂停图标显示，开关暂不可操作；不能改成关闭，造成设置丢失的错觉。
上方目标名称同样弱化并保留暂停标记，仍可点击编辑；保存后反馈“已保存，切回 Rule／Direct 后生效”。
这是一处页面级状态，不为每个 App 重复添加解释段落或反复弹提示。

开关位置表示用户保存的启用意图；颜色区分四类采用状态，图标解释原因。
正常状态不增加一排文字；异常点开名称查看原因并选择新目标，不设批量修复入口。

| 状态 | 开关显示 | 含义与操作 |
| --- | --- | --- |
| 已关闭并采用 | 左侧、中性色 | 当前不使用该 App 的单独规则 |
| 已启用并采用 | 右侧、主题强调色、确认图标 | 规则已采用，不保证节点连通或已有连接命中 |
| 已启用但未参与 | 右侧、等待色，默认琥珀色系 | 暂停图标表示 Global；电源表示 VPN 未启动；范围图标表示未纳入 VPN |
| 已启用但配置异常 | 右侧、错误色、断链／警示图标 | 目标缺失或采用失败，需用户处理 |
| 正在采用开／关 | 保留用户新位置、等待色、小型加载标记 | 在途更新，以最后一次操作为准 |

关闭请求失败时也要显示错误状态；不能因为开关已在左边就声称旧规则停止生效。
本地保存失败回到旧值并提示；如果原规则仍正常采用，不将原健康状态持续标成错误。
确认配置失效时保留错误色及具体原因；Global 暂停仍由页头表达，失效应用规则不阻塞 Global。
Global 下原本关闭的项仍为左侧，不必再加暂停图标。
四类颜色分别采用中性、强调、等待和错误语义，随主题适配明暗，不仅使用开／关两种填充。
不以色相作为唯一提示，图标、原因及可访问名称仍共同表达状态。
用户主动选择 REJECT 属于正常采用，用强调色；不能与配置故障的错误色混淆。
参考 [Android Switch][switch] 的二态及图标能力，
并采用 [W3C Use of Color][color] 的颜色补充信息原则。

[switch]: https://developer.android.com/develop/ui/compose/components/switch
[color]: https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html

页面不为保存设置自动 Start，不自动切模式，不自动接受来源；VPN 未启动的保存反馈为下次启动生效。

一个普通“代理开关”无法同时表示跟随规则、明确直连、拒绝、指定目标等策略。
因此这里的开关始终表示“启用该 App 的单独策略”，短摘要明确策略内容；不能把 Rule 下的关闭标成直连。
在最常用的 Direct＋少数代理应用场景，首次开关正好对应开启该应用的代理，关闭恢复直连。

## 4. 多数应用直连的完整操作

1. 添加并接受所需节点，选择当前订阅；在 Proxies 中准备一个可用代理组。
2. 选择 Direct，点击 Start；先后顺序均可，保存策略本身不负责启动 VPN。
3. 打开应用网络，设置“应用代理组”，例如已有的 g-us-byg。
4. 打开 Chrome 的单独策略开关，其默认使用该组；其它应用保持关闭。
5. Chrome 发起新连接后，在其 Host／连接页确认命中本地应用策略和实际代理出口。
   其它应用的新连接显示 Direct；没有近期活动的应用可通过“显示所有应用”找到并设置。

无需逐条关闭订阅中的几十个来源，不改订阅规则，也不将未启用应用交给订阅的 MATCH 兜底。
切换到 Rule 后，关闭单独策略的应用重新遵循 Rule；要在 Rule 中明确直连，须启用其默认直连策略。
切换到 Global 后，全部应用策略暂停，Chrome 同样使用 GLOBAL 组。

## 5. 订阅处理保持现状

沿用 FlClash 现有的订阅下载、已接受材料、DNS、分组、监听、来源许可和配置准备流程。
Rule 中只将本地应用策略叠加在原分流路径之前；Direct 中应用策略未命中后仍由原 Direct 分支处理。
不新增节点专用投影、DNS 替换、rule-provider 裁剪或递归限制订阅组成员的机制。

指定现有组或节点时复用其原有选择、健康检查和回退语义；组内本来允许 DIRECT 等成员的设置不被本功能重写。
所以开关强调色表示本地规则已采用，不能据此声称该组最终一定走了代理；真实出口继续从连接事实核对。
配置接受和来源权限保持原边界，本地策略编辑不自动接受待审材料，也不主动要求全量重新下载。

独立的“订阅只提供节点”方案会处理更强的需求：订阅 DNS 选择不能影响解析，
显式为 DNS 指定的代理出口也被移除，以及启动不再等待无关规则资源。
当前 Core 的 [DNS 配置](../../../core/Clash.Meta/config/config.go)和
[DNS Dialer](../../../core/Clash.Meta/tunnel/dns_dialer.go)
允许按 nameserver-policy 选解析器或显式选代理组；仅跳过业务分流规则不等于改变这些独立设置。
respect-rules 则沿真实模式匹配，不能声称它单独就会绕过 Direct。
这些是纯节点订阅模式的可能目标，当前应用策略需求不包含这类全面隔离，故不增加对应实现。

## 6. 保存、范围与失败反馈

应用策略作为用户全局配置独立持久化，以当前 Android 用户内的 package name 标识，
不写入订阅文件、不持久保存临时 UID。公共应用代理组与 App 独立组引用也进入备份。
自建组以既有全局组 ID 引用；订阅组引用包含所属 Profile，不能切订阅后凭同名自动替换目标。
切订阅不会清除应用开关及策略；通过下一节的按订阅绑定、恢复及失效排序处理目标问题。
应用规则与绑定使用既有 Drift 数据库持久化，写入沿现有 Request／配置采用边界。

### 6.1. 切换订阅时的恢复

全局保存应用启用意图和规则；具体目标另外记住每个订阅的绑定。
例如在 A 订阅选择香港组，在 B 订阅选择美国节点，之后 A → B → A 时分别恢复各自选择，
不清空开关，不把 B 的修复覆盖到 A，也不要求用户每次切换重新设置。
策略选择页明确显示当前订阅；普通更换组／节点只改变当前订阅绑定，启用意图仍全局一致。

切换后按下列顺序解析目标：

1. 有该订阅以前保存且仍可用的绑定：直接恢复。
2. 引用同一全局自建组 ID，且当前订阅有可用运行组／成员：直接复用。
3. 其余情况保留为待处理项；点击名称进入选择页，跨订阅同名不能自动当成同一目标。

订阅正在准备、provider 尚在加载、Core 暂未就绪时，标为核对中，不提前判定目标已删除。
这段时间沿既有准备流程处理，不另起全量下载；完成后只对仍然缺失／不可用的目标要求修复。
来源待审则指出需要原有审核，不用重新选一个同名目标绕过许可。
关闭的应用策略不影响切换，也不因旧目标问题前排；下次启用时再校验并引导选择。

同一订阅更新也会造成改名或失效。自建组按全局组 ID 追踪，改名只更新显示。
没有稳定身份的订阅组／节点原名消失时标为失效，前排引导选择；首版不额外开发指纹匹配改名系统。
现有 cache-identity 用于出口缓存，不是完整路由身份，不能直接拿来自动迁移目标。
目标仍存在的正常已接受更新沿原订阅语义处理，不按地区字样、相似名称或列表首项猜测替代。

### 6.2. 失效项前排，逐项处理

取消批量修复页面、处理总入口和自动修复弹窗。应用列表将需要用户处理的失效项排在前面，
以应用代策略开关组件的错误色和原因图标直接显示；点击上方名称进入新选择页重新选择目标。
选择页显示原目标完整名称和当前订阅，选好保存后返回原列表上下文。

默认列表同时纳入已启用应用规则的 App，即使它没有近期活动，不能因原列表只显示观察记录而藏起失效项。
当前搜索范围内先排失效项，组内沿用近期活动排序，其余项目保持现有排序。
排序在进入页面、切订阅核对完成或编辑完成后更新；滚动和点击期间保持项目身份及可见位置，
不因每次连接轮询反复跳位。关闭的旧策略不因目标过期而抢占前排；关闭尚未成功等采用故障仍需前排提示。

公共组的正常设置入口保留，修改公共组会自然影响跟随它的应用，但不再制作专门的批量修复流程。
替换只修改当前订阅的绑定，不改其它订阅绑定或自建组定义。切回订阅恢复其上次有效选择。

未修复的启用代理规则不静默直连，也不阻塞无关应用使用新订阅。候选配置对确定缺失的目标
使用明确的本地保护结果，拒绝相关新连接，并在选择页显示“选择目标后恢复”。
准备期间沿现有流程保留可用旧运行配置；只在新配置实际采用后才显示新的保护状态。
原有效配置已无法保留时，也不把缺失目标改成订阅 MATCH／首个节点。
旧连接仍按既有生命周期保留，不改写观察记录。

用户也可主动关闭该应用规则；这会跟随当前模式，须明确说明
Direct 下恢复直连、Rule 下恢复原规则，不能将两者都标为直连。
Global 中这些规则本就暂停，失效项仍可显示和处理，但不影响全局代理，也不自动弹窗。

### 6.3. 保存与采用反馈

保存意图、实际采用和历史连接保持独立。开关先即时反映本次编辑，只有 Native／Core
确认采用对应版本才算生效；不通过开关位置或延时推断成功。

| 情况 | 可见反馈与实际处理 |
| --- | --- |
| 保存失败 | 开关恢复最近已保存值，提示原因，可再次操作 |
| 运行中采用 | item 局部加载，不遮挡或清空列表；连续编辑合并，以最后一次为准 |
| 已采用 | 简短成功反馈；新连接才按新策略处理，旧连接不伪装成已改道 |
| 应用失败 | 保留已保存设置，显示“尚未生效”及重试，保留可确认的原有效状态 |
| 指定组／节点失效 | 保留名称及启用意图，错误色加原因图标并前排；点击名称进入选择页 |
| 待审核节点或材料 | 可保存意图，不能借此批准来源；不自动弹出审核并阻塞列表 |
| 应用被 Access control 排除 | 标明不参与 VPN 分流，提供修改原接管范围的入口，不暗中扩大范围 |
| VPN 未运行／Global | 按上一节显示待启动／策略暂停，不冒充已生效 |

失效只阻止相关代理策略落到错误目标，不把所有应用自动改成直连，也不默默选择首个同名组。
停止 VPN 的新意图始终胜过在途采用；较新的模式、订阅和策略变更使旧结果失效。
本地策略更新不下载全量订阅，不要求重新审核已接受节点。

未知应用不能被创建确定的单 App 策略；在 Direct 中未识别连接遵循 Direct，在 Rule 中遵循原规则。
身份识别失败可能使某个 App 的例外无法命中，必须保留诊断事实，不按域名或前台应用猜测。
共享 UID 若无法独立分流，按整个共享身份处理；UI 明确列出受影响应用并取得一次明确确认。

### 6.4. 数据规模与清理

仅保存用户实际配置的应用规则和实际选择过的订阅绑定，不预生成“所有应用 × 所有订阅”，
不保存节点列表快照或每次切换历史。同一绑定更新原记录；公共组被多个 App 引用时只保存一份绑定。
例如 20 个 App 跟随公共组，在 A、B 订阅各选一次目标，是 20 份应用设置和 2 份公共绑定，
不是为每个 App 复制两套节点数据。DIRECT、REJECT 和未设置整应用默认动作都不需要节点绑定。

绑定是用户配置，不套用出口 IP 缓存的有效期，也不因长期未切订阅而删除有效选择。
“目标暂时缺失但仍被规则引用”是待处理配置，不是垃圾，须保留名称及规则供用户恢复。
以下简化只针对应用策略绑定，不改变已实现的出口 IP 缓存到期清理。

只保留两类必要的引用变化，在持久化层同一事务中处理，页面不各自挂清理逻辑：

| 必要入口 | 清理范围 |
| --- | --- |
| 真正删除订阅 | 删除该订阅绑定，优先由外键级联保证；保留全局应用规则及其它订阅绑定 |
| 删除／重置规则、删除或替换绑定 | 统一配置写入流程检查受影响目标，删除已无引用的记录，不维护另一套引用计数 |

导入／恢复同样走该写入约束和订阅 ID 映射，不另建定时清理、页面进入清理或卸载扫描任务。
应用卸载、规则关闭、订阅暂未加载及目标暂缺都不自动删配置；用户删除相应规则时才处理引用。
没有目录权限也不能当成应用已卸载。有效但很久未用的绑定仍是用户设置，不作为垃圾清掉。

### 6.5. 目标可用性的必要更新入口

目标校验不等于清理。订阅更新后组暂时没有节点，应保留定义及引用、更新状态，而不是删除绑定。
校验和成员重算收敛到既有配置／分组解析链路，页面只消费结果，不各自轮询、重跑正则或扫描数据库。

| 触发入口 | 所需工作 |
| --- | --- |
| 当前订阅的已接受节点／分组资源版本变化 | 沿既有链路解析受影响组，生成节点和组可用状态，再校验引用它们的应用规则 |
| 用户保存应用规则或启停规则 | 校验本次目标，复用当前解析结果，不重新匹配所有正则 |
| 模式或 VPN 状态变化 | 更新规则是否参与及采用状态，不清理数据、不重算节点成员 |

第一项涵盖切订阅就绪、订阅更新获准采用、节点 provider 材料采用，以及自建组定义编辑／启停。
只处理当前准备／应用的订阅及其相关启用组，不重算所有订阅的全部历史绑定。
重算按节点／组定义的相关版本去重，不因测速数字、当前选中成员或连接数变化反复执行。

既有 [Core 成员解析](../../../core/local_groups.go)和
[provider 采用时刷新](../../../core/local_group_refresh.go)已具备重新匹配表达式的路径。
复用这些路径，补齐对 UI 的可用状态输出，不能在应用网络再引入第二套正则匹配器。
有正则的组在当前已接受节点中重匹配并扣除手工排除项；手选组取当前节点交集。
自建组名称和 ID 仍存在，不代表它有可用成员。

状态由同一解析结果提供给应用代策略开关组件、新选择页与 Group management：

| 分组结果 | 统一反馈 |
| --- | --- |
| 资源仍在准备或候选尚未采用 | 显示准备中／待应用，不把临时空列表认作无节点；沿用仍有效的运行事实 |
| 正则无匹配、匹配全被排除或手选节点全缺失 | 管理页明确显示对应原因及 0 个可用成员；引用该组的启用应用规则显示异常并前排 |
| 自建组被禁用或未加入当前订阅 | 显示禁用／未绑定原因，不能与正则无匹配混为一类 |
| 更新或编辑后恢复成员并成功采用 | 自动恢复可用状态，原应用开关与目标引用保留，不要求重新选同一组 |

管理页节点数要区分保存的选择数和当前可用成员数，不能以保存数量代替运行结果。
当前空组的 REJECT 占位不能被计成一个可用节点；用户主动设置应用 REJECT 则是正常有效策略。
有真实成员但测速暂时全部失败不属于配置失效，继续由原分组健康检查处理，不新增网络探测。
Group management 仅增加这些必要状态提示；原 Proxies 选择页及其选点逻辑保持原样。

## 7. 实现依据与必要增量

当前 [Core 模式分派](../../../core/Clash.Meta/tunnel/tunnel.go)在 Direct／Global 中直接选择出口，
只有 Rule 调用规则匹配。因此只追加 PROCESS-NAME 规则无法实现 Direct 下的应用例外。
不能将 Core 偷换成 Rule、却继续向 UI 报告 Direct，这会让模式查询、外部控制与采集事实冲突。

需要在共同 TCP／UDP 路由路径增加本地应用策略阶段：Global 保持原分支；Rule／Direct
以可信应用身份评估已接受的本地策略，未命中再进入原模式路径。匹配结果须进入既有来源追溯，
记录本地策略 ID、版本和原应用身份，供现有连接详情验证；不能在 UI 用当前设置反算旧连接。
配置合成、指纹、接受凭据和原版本 fence 必须包含这份本地策略，远程订阅不能声明同等权限。

优先在父 Core 现有边界实现；模式分派缺少可用扩展点时，仅为该新能力增加必要的 mihomo 扩展，
再更新完整源码 carrier。它是新增路由能力，不是借任务修复或重构整个 Core。
应用身份沿用任务 01 的可靠事实，不能把旧 Process／UID 的任意首个包当作授权主体。
使用已有 ConfigInput／Setup 采用流程；VPN 范围变化仍由 ServiceState 管理，UI 不建立第二个生命周期所有者。

## 8. 交付顺序与验收

本轮将 05／06 作为连贯交付：05 保留逐应用修改接管范围的闭环，放在 App 页菜单和原
Access control 中；06 交付全局持久策略、模式分派、主列表即时采用、按订阅恢复及统一分组状态。
主列表开关属于 06 的应用策略，不能只交一个没有实际分流效果的开关。
07 在同一模型增加 App＋Host 和跨 App Host 操作，并落实本方案的模式差异；08、09 继续承担快捷入口与整体验收。
实施限于 05／06 及已批准的分组状态提示，不恢复已暂停的安全 Loop；07–09 不提前标为完成。

验收使用两个可确定身份的 App，对同一目标分别建立新 TCP／UDP 连接；真实 Android 结果是完成条件，
规则文本、mock 和开关显示不能代替出口验证。至少覆盖：

- Rule／Global／Direct 与关闭、直连、REJECT、指定组／节点的组合，切模式保留策略，Global 忽略应用规则。
- Direct 中未启用 App 直连、启用 App 按本地策略处理；Rule 中应用策略优先于订阅规则，
  无应用策略时原有订阅、DNS、来源准备和模式行为不变。
- 组件一／两行高度预算、长名称、窄屏、大字体、名称与开关独立点击、选择取消及保存失败。
- 新选择页仅提供 DIRECT／REJECT 及目标选择，无“跟随模式”重复项；关闭开关恢复模式路径但保留设置。
- 搜索、分组／节点和返回上下文正确，原 Proxies 选点代码及 Dashboard outbound mode 均不改。
- 目标准备中不误报失效，A → B → A 恢复各自绑定；自建组改名按 ID 跟随，无稳定身份的目标不猜。
- 失效配置前排且无活动时仍可见，选择替代目标不改其它订阅，滚动／操作期间不乱跳；
  关闭策略后不遗留 App＋Host 例外，Global 不受失效应用目标影响。
- Rule 中应用策略优先于来源规则；07 验证两个 App 同一 Host 的不同出口，以及 Direct 忽略跨 App Host 规则。
- 订阅更新、切换、同名分组、删除／禁用分组、共享 UID、未知身份及重装不误套策略。
- 停止时编辑不启动 VPN；快速切换、Stop、失败、旧响应和重启恢复符合上述采用语义。
- 四类颜色区分关闭／采用／待生效／异常，图标表达原因；主动 REJECT 不误报配置故障。
- 删除订阅、规则重置及替换目标在统一事务清理孤立数据；打开页面、切模式、卸载应用不触发配置清理。
- 已接受节点变化后，正则零匹配、排除后为空及手选交集为空正确同步到管理页和应用状态；
  成员恢复后自动恢复状态，REJECT 占位与暂时测速失败不冒充成员或配置故障。
