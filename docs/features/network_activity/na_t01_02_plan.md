# 02 内存汇总与应用活动只读页 Plan

任务入口：[NA-T01-02](network_activity_tasks.md#na-t01-02-内存汇总与应用活动只读页)，实施基线 7dea604。
本项交付 Tools → 应用网络入口、第一层只读页及三层页面可共用的运行期汇总。
03、04 的目标页面和 05–07 的编辑操作仍由各自任务交付。

## 问题与目标

01 已输出可用的应用身份和冻结连接事实，但 Requests 仍为流水，不能按 App 判断活动及出口。
用户需要打开一个实际页面，看到当前／近期活动过的应用、活跃连接数、近期连接次数、最近活动及实际规则／出口，
可以搜索并切换当前活动、近期活动、全部应用。断开时仍可看保留结果，页面不启动代理、下载订阅或接受来源。

## 方案与理由

汇总复用原 Core request 事件和 getConnections；纯内存连接集合最多保留最近 4096 条，
以 Native runtimeEpoch＋连接 ID 去重。App、App＋Host、Host 跨 App 查询使用同一集合，
次数表示保留的连接数，不代表 HTTP 请求数或完整历史。超限淘汰最早保留记录并显示覆盖受限。
确定包名才归入对应应用；共享 UID 和未知身份单列，域名未知时使用原 IP，不推测归属。
规则、出口、版本及来源沿用首份连接事实，只更新实际流量计数和活跃观察，不以当前配置反算旧记录。

观察由应用级 provider 承载，并由 CoreManager 在 Android 启动时保持，页面只读取结果。
观察器等待现有 initProvider 确认初始化完成后，才读取 Native／配置状态，不抢占 bootstrap 的依赖初始化；
开始观察时从现有 Requests 的最多 2000 条内存事件补入同实例记录，再由完整快照校对。
request 补足短连接；约两秒的前台快照校对存活，重复观察不重复计数。
只有完整且前后运行上下文一致的成功快照才能确认结束；快照返回期间新增的事件不被该快照判为结束。
事件自身不证明此刻仍存活，等待快照确认。无效返回必须失败，不能变成空快照。
Core 实例由现有配置事实确认；异实例迟到事件、断开／重连前的异步结果不能混入当前状态。
停止观察保留近期记录并使活跃状态待确认；Core／Flutter 进程重启或清空后重置内存。
清空不改规则，也不把清空前仍存活的连接重新计为新活动。

后台仍接收原通道实际送达的事件，暂停主动快照，返回时立即校对并标记可能的观察缺口。
不新增 Android 后台常驻或历史补发保证。离开页面不会停止观察；快照失败保留旧记录并显式显示待确认。
查询结果、容量和缺口保持不可变，向后续页面提供同一观察范围。

页面使用现有 CommonScaffold、应用图标、列表及搜索样式，显示观察状态和简短范围说明，保留旧内容而非整页加载遮挡。
近期列表以有活动的 App 为主，全部应用复用安装应用目录；目录加载失败不隐藏已识别活动，并提供重试。
接管范围仅显示现有设置的含义，TUN 证据与设置分别处理；无法证明当前实际接管时不标为已生效。
多规则／多出口显示概况；条目可展开查看只读摘要，03 实现后再接目标列表，不放空跳转或编辑控件。
文案维护四种 ARB 并生成本地化；具体间距、筛选控件及空态在本项实现中细化。
