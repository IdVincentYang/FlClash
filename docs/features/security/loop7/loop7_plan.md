# Loop 7：Android 集成验收与使用结论

本轮判断前六个 loop 的成果在实际 Android 发布包中是否一起生效，形成“在什么版本、配置和环境下可以怎样使用”的结论，而不是仅报告编译或扫描通过。当前是待 review 的阶段方向，确认后再细化验收安排。

## 需求与需要保留的能力

用户最终需要可安装、可持续上网的工具，订阅自动刷新、常用站点诊断和本地 bug 证据也要正常工作。同时需要知道敏感数据交给谁、故障时流量怎么处理、哪些风险已经解决、哪些仍需选择或限制。

目标是把源码修复、构建输入、最终 APK、Android 行为与剩余风险对应起来，让使用结论有证据和明确适用范围。

## 风险与不做整体验收的后果

| 集成风险 | 为什么单轮结果不足 | 不验收时可能发生什么 |
| --- | --- | --- |
| 源码与安装包不同 | SDK、manifest 合并、release 优化、签名/环境配置和缓存都参与产物 | debug 或源码中的保护可能没有进入用户安装的包，或 SDK 被传递依赖重新引入 |
| 跨轮策略冲突 | 请求路由、订阅更新、配置接受、DNS、监听认证、Geo 更新相互影响 | 一处修复被另一处回退或绕过；也可能无法刷新/联网，使用户被迫关闭保护 |
| 生命周期与真实网络 | 启动、重启、VPN撤销、SSID/IPv6、断网恢复和系统后台限制影响实际行为 | 静态判断正确但故障期间发生直连、DNS外泄、旧任务外发或错误状态提示 |
| 证据不足与版本漂移 | 扫描、短时无流量、签名验证各只证明部分范围；上游同步会改变输入 | 把局部通过误写成零风险，或把旧证据用于已经变化的新 APK |

## 验收思路与取舍

- 绑定受审主仓库/核心提交、依赖与数据版本、工具选择、应用环境、ABI/API范围、APK摘要和签名。以实际发布配置检查依赖、manifest、库与资产，不以打包成功替代运行验证。
- 在独立、可控 Android 环境验证正常上网与故障行为：应用外发、业务流量/DNS、订阅自动刷新、所选站点诊断、本机访问、导入/备份/恢复、Geo 更新及崩溃证据形成连贯使用闭环。
- 同时覆盖“允许的功能能工作”和“未允许的行为被拒绝”。真实出口/接收端观察与源码、测试和产物核对相互支持；证明关键回归能发现保护丢失，而不只统计通过数量。
- 使用合成订阅、凭据和二维码，本地代理/受控目标，区分系统网络噪声及 SDK 代发；不把用户真实流量、配置或 dump 发给测试服务。测试设备和系统路由变更按当时授权安排。
- 对每项基线及新增发现核对处理结果，区分已修复、未影响、缓解、仍未解决和未验证，并绑定理由、证据和复核条件。重大未闭合风险不能被“用户已读提示”自动放行。
- 将受影响的回归入口与冲突理由保留在现有计划/验收记录，官方同步、依赖/数据升级后重新核验变更范围。日志、抓包、APK 和符号留在本地，不为每次编译新增结果文档。

## 整体验收的收益与代价

收益是发现单轮没有暴露的交互问题，并让最终使用结论对应真实产物。代价是需要受控设备、发布范围内的 API/ABI 与故障验证；覆盖不足会推迟可作安全承诺的范围。

不能只追求“没有任何网络请求”，那会破坏代理、订阅和诊断需求；也不能把功能能用当作没有泄漏。是否允许直连、共享代理或自定义来源，应与已确定的用户策略一致。

## 依赖、完成方向与结论边界

- 依赖 [Loop 1](../loop1/loop1_plan.md)、[Loop 2](../loop2/loop2_plan.md)、[Loop 3](../loop3/loop3_plan.md)、[Loop 4](../loop4/loop4_plan.md)、[Loop 5](../loop5/loop5_plan.md)、[Loop 6](../loop6/loop6_plan.md) 的实际交付；输入变化或跨轮问题返回所属阶段处理，不在验收中悄悄修改安全策略。
- 发布范围、代表性配置与验证条件需要 review 后确定。完成时正常能力与关键安全边界均有证据，失败/跳过/未验证明确说明，受测 APK 与最终交付输入一致。
- 使用结论回答：是否发现未告知外发、未授权直连/DNS出口、凭据泄漏、来源未知资产或可达重大漏洞；剩余问题在哪里、何时触发、如何缓解，是否阻止当前版本使用。
- 结论仅对受审版本和条件有效。代理、订阅服务、DNS与目标网站仍能看到处理服务所需的元数据；客户端不能保证匿名、第三方服务可信或操作系统未被攻陷。
- 后续交付和上游同步遵循 [CONTRIBUTING.md](../../../../CONTRIBUTING.md)；本轮不替代用户对发布 APK、安装到个人设备或上传证据的授权。
