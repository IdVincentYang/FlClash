# Loop 6：Geo 数据来源、完整性与更新

本轮确认 GEOIP、GEOSITE、ASN 及相应 MMDB 等路由数据是否对应可信发布，并防止更新渠道或本地文件改变路由判断。对应[审计基线](../android_security_baseline.md) A-07。当前是待 review 的阶段方向，确定后再拆任务。

## 需求与需要保留的能力

用户需要按域名、国家/地区与网络归属分流，也需要数据更新跟上网站和网络变化。数据是规则判断的重要输入，删除全部 Geo 文件或永久停更可能使依赖这些规则的配置不可用。

目标是同时保证来源可核验、格式可使用和更新不会破坏已有可用数据；每份文件要有明确发布者与版本，“官方”不能只指一个模糊仓库名称。

## 风险与不整改的后果

| 风险入口 | 当前事实与待核实边界 | 不处理时可能发生什么 |
| --- | --- | --- |
| 内置文件历史来源 | 与审查日 rolling latest 不同，历史发布对应尚未闭环 | 无法区分正常旧版本、生成/筛选差异与实际修改，也不能向用户证明旧文件未被篡改 |
| latest 与自定义来源 | 下载目标可变化，缺发布者签名或独立可信预期摘要约束 | 来源被替换、发布渠道被攻陷或指向非预期资产时，可能接受错误数据 |
| 数据影响路由 | 域名/IP/ASN 分类会影响依赖它的规则 | 数据错误可能使目标匹配到错误节点或 DIRECT；实际后果取决于配置，数据文件本身不等于可执行代码 |
| 更新和热加载 | 核心已有格式、内容变化及并发处理，发布来源校验仍未闭环 | 格式正确的非预期数据可能被接受；下载/保存/重载失败也可能使规则不可用或状态不一致 |

哈希新旧不同不能直接认定篡改。核心用来判断“内容是否变化”的哈希，也不能代替与可信发布资产的身份比对。

## 解决思路与取舍

- 为内置及运行中使用的每份数据建立发布者、仓库/生成来源、固定版本/提交、资产名/格式和摘要记录，比较同一版本、同一资产。需要从源码生成时绑定生成工具与输入数据，解释可复现性差异。
- 能找到旧发布时独立比对；找不到时明确“历史来源无法证明”，在 review 后用已核验发布建立新基线。不能用新文件可信推导旧文件从未被修改。
- 对下载先验证 HTTPS/目标和发布身份，再验证可信摘要或签名、格式、资源限额与代表性规则行为。信任根必须独立接受，不能让被替换的下载源同时提供文件和唯一可信校验值。
- 覆盖内置载入、首次缺文件补齐、手动/定时更新和核心内部下载，避免只保护设置页。先验证再替换，失败保留已知可用版本；磁盘故障、取消、并发与热加载也需有确定结果。
- 保留数据更新能力，在本地展示版本与来源，评估显著路由分类变化；自定义数据源要有明确的信任选择和策略。只停更会累积数据陈旧风险。

## 整改收益与代价

收益是能回答每份文件来自哪里、是否与接受的发布一致，并降低格式正确但来源不可信的数据进入路由的机会。代价是首次溯源、可信摘要维护和版本更新复核；不同生成数据集也可能改变现有规则表现。

需要 review 的是信任的发布者、旧来源未知文件的替换方式、自定义来源政策以及重大分类变化的处理。发布者签名不能证明数据分类永远正确，仍需结合 [Loop 2](../loop2/loop2_plan.md) 的路由约束与实际行为验证。

## 范围、依赖与完成方向

- 使用 [Loop 1](../loop1/loop1_plan.md)的下载/凭据/出口边界；本轮负责数据身份与可用性，规则接受策略归 Loop 2，解析器漏洞归 [Loop 4](../loop4/loop4_plan.md)，其它嵌入资产归 [Loop 5](../loop5/loop5_plan.md)。
- 完成方向是每份启用数据均有接受的来源/版本及比对结论，正确更新可用，错误摘要/格式/来源与失败更新被拒绝且不破坏原数据。
- 运行结果能够对应实际使用的数据版本和规则，历史未知项如实保留结论；不以与当前 latest 一致代替全部历史审查。
- 优先复用现有核心下载/更新边界并维护窄补丁，避免 fork 出平行更新器；官方同步按 [CONTRIBUTING.md](../../../../CONTRIBUTING.md)复核来源、格式和校验路径。
