# Loop 6：Geo 数据身份、内容影响与可信更新

本轮确认 GEOIP、GEOSITE、ASN 及相关 MMDB 是否对应接受的发布，解释历史差异，并保护正常更新及路由使用。依据[共同安全目标](../security_requirements.md)，对应[审计基线](../android_security_baseline.md) A-07。
2026-11-06用户保持“不改Core”，将T02／T03移入[后续备忘](../deferred_security_items.md#loop6-t02t03-geo-更新与实际采用)，并决定本轮按调整后的范围完成。
已交付的是T01固定随包基线／离线核验及T04 Android内置缺失seed核验；全入口运行期更新保护、真实热采用和正式版本界面没有因此实现。
单层[任务定稿与交付历史](https://github.com/IdVincentYang/FlClash/blob/f73b5464f73ba8cd352f93b4bd258998a8d6daf7/docs/features/security/loop6/loop6_tasks.md)保留在结案提交；当前不再有活动任务清单，不按旧连续授权恢复延期事项或启动其它Loop。

## 本轮闭环与顺序

先建立可复核的随包数据基线，再让所有下载／初始化入口消费同一接受规则，最后核对界面声明与真实分类／路由使用。
首项完成不能推导私有缓存已获信、运行中的reader已切换或自动更新已受到发布校验保护。

1. 数据溯源与可信基线：核同版本资产、APK对应和历史结论，形成固定基线及离线验证入口。
2. 全入口可信更新：覆盖seed、首次补齐、手动／自动／Core内部更新，先校验再替换，失败保留及真实重载；维护正常自动更新。
3. 可见版本与消费验收：沿现有English Resources入口显示来源／版本／采用事实，以真实Core分类和独立路由收件核实所用版本。

T01设计通过前只做只读调查、必要公开下载比对和设计文档，不替换资产、改生产／生成、构建或启动应用。
后续任务在其前置项实际交付后细化设计，不从本轮方向直接取得尚未评审的生产方案。T04仅依赖T01，作为独立missing seed出口，不替代T02／T03。
上述原完整闭环保留为延期目标；本次结案采用用户明确调整的范围，不把未实施项记成验收通过。

## 共同职责与限制

发布身份／精确payload基线由应用包装层维护，沿既有Request／Source票据、ConfigInput／T01、格式锁和commit receipt接入；
ServiceState仍只管理运行意图，Core既有parser／matcher仍负责分类，不能另造matcher或运行状态权威。
已加载reader、磁盘文件和下载候选是不同事实；URL、mtime、同一渠道附带hash及格式通过都不能单独证明接受的发布身份。
自定义源必须有明确的接受依据与自动维护范围，不能以任意URL或“下载成功”自动建立信任。

运行期范围为Android，不扩大有限受管Geo语法，不恢复Loop3／L1-T04／T05，也不启动其它Loop或网络活动后置需求。
Core／依赖源码、gitlink、carrier保持不改；发现包装层无法覆盖的实际入口时，带消费者、缺口及替代方案交M，只暂停受影响部分。
DNS R1及Core完整安装日志并发仍未解决，本轮Geo结论不得升级它们。
验证默认本地合成及loopback；若任务确需设备，先在方案说明最小安排，仅用原Pixel_7a_API_34和原userdata，
不克隆／wipe／改global ADB或宿主网络，不引入真实订阅、秘密、用户DB和公共业务测试流量。

## 需求与正向价值

按域名、IP、地区和 ASN 分流需要数据支持，也需要跟随网络变化更新。目标是让每份启用文件有明确发布者、版本、来源和比对结论，并说明它怎样影响接受的规则。

真实发布、传输完整性、分类准确和最终路由分别判断。用户接受的 DIRECT 规则可以保留，数据被错误修改而扩大直连或更换节点才需要按实际影响处理。

## 风险与不整改的后果

| 风险入口 | 当前事实与待核实边界 | 不处理时可能发生什么 |
| --- | --- | --- |
| 历史文件差异 | 当前文件与审查日 rolling latest 不同，旧发布对应未闭环 | 无法区分旧版本、生成/筛选差异与篡改，不能证明历史文件身份 |
| 下载与发布身份 | latest 可变化，缺独立接受的版本/摘要或发布者签名约束 | 错误资产、渠道替换或发布者被攻陷的内容可能被当作正常更新 |
| 分类影响规则 | 数据是节点/DIRECT 等匹配的输入，实际影响取决于配置 | 特定域名/IP 被分到非预期出口；官方分类错误也能导致错误判断 |
| 替换与重载 | 现有核心有格式、内容变化及并发处理，发布校验未闭环 | 格式正确的错误文件被接受，或失败更新破坏可用数据/运行状态 |

数据文件不因参与路由就成为可执行代码；解析器缺陷归 Loop 4。新旧摘要不同只说明内容不同，不能独立证明篡改。

## 解决思路

- 为内置、缓存和运行中使用文件记录发布者/生成来源、固定发布或提交、资产名/格式、摘要及下载渠道。优先找同一发布者、同一版本、同一资产比较；若有本地加工，绑定工具与输入并解释差异。
- 对旧文件保留明确结论：与可信发布一致、已知加工差异、确认异常或历史无法证明。无法溯源时处置现用文件并建立新可信基线，不能用新文件可信推导历史未篡改。
- 核验传输与发布身份，优先使用可验证签名或独立接受的版本/摘要。区分阻止传输替换与防范发布者自身被攻陷；同一未经信任来源同时提供文件和摘要不构成独立证明。
- 比对必要的内容统计和代表性规则，检查异常分类变化，说明数据准确性的证据与限制。重大变化处理依据来源信任与影响决定，常规可信更新继续可用。
- 覆盖内置加载、首次补齐、手动/定时更新和核心内部路径。先验证再替换，失败保留已知可用版本；磁盘错误、并发、取消及热加载结果与实际文件版本一致。
- 自定义来源保留用途和明确的接受策略，说明校验证据与可见范围；不以永久停更或强制删除 Geo 能力代替处置。

## 收益与代价

收益是能回答文件是否与接受的发布一致，降低被替换数据影响路由的机会，也防止失败更新破坏分流。代价是旧文件溯源、可信版本维护与数据变更复核，替换数据集可能改变已有规则结果。

细化时确定受信发布者、旧来源未知文件的替换方法及自动更新校验方案。证据强度如实说明；发布签名能证明发布身份，但准确性和发布者自身可信仍有边界。
