# Loop 2：配置接受、实际路由与 DNS 行为

本轮让导入、刷新与配置合成后的实际路由符合接受的配置，防止隐藏改道、超出订阅信任范围的变化及错误的保护提示。依据[共同安全目标](../security_requirements.md)，对应[审计基线](../android_security_baseline.md) A-04、A-13。阶段已细化为[单层任务清单](loop2_tasks.md)，任务归属、执行状态及实际交付由该清单维护。

用户于 2026-10-15 同意优先推进本阶段及首项任务。先形成首项设计并由 M 评审，再按授权连续实施、验证和交付；具体归属、授权与当前阶段由任务清单维护。Loop 1 的 L1-T04 仍按用户决定暂缓，本阶段不把该风险记作已解决。

## 需求与正向价值

保留订阅导入和自动更新、规则分流、节点选择、健康检查及 DNS。用户接受的 DIRECT、局域网、分应用和节点启动解析具有正常用途；判断安全需要知道哪些配置由用户指定，哪些更新授权交给所选订阅源。

目标是让最终生效配置、实际连接和界面显示一致。常规节点/规则更新在接受的范围内继续自动执行，高影响变化和超出信任范围的输入有明确处理。

## 风险与不整改的后果

| 风险入口 | 当前事实与待核实边界 | 不处理时可能发生什么 |
| --- | --- | --- |
| 订阅与远程 provider | 输入可改变节点、规则、DNS 和资源来源；应用已经覆写部分字段 | 来源被攻陷或被替换时，可能引入窃取流量的节点、扩大直连或增加接收方 |
| 合成、脚本与覆写 | 订阅、脚本、用户覆写和应用策略共同形成最终配置 | 原始 YAML 看起来正常，最终策略却与选择不符；新字段也可能绕过限制 |
| 业务数据处理 | 核心、插件、统计和日志路径对流量内容的实际处理需要走读 | 若夹带镜像发送或额外内容记录，正确规则也可能伴随隐蔽收集 |
| DNS 路径与启动解析 | 默认有第三方解析服务，系统/TUN/加密解析及 IPv4/IPv6 的实际路径需验证 | 未接受的 DNS 接收方或回退获得查询；所选加密 DNS 自身仍能看到解析内容 |
| 状态和故障行为 | VPN 撤销、断网、排除应用/网络及核心失败影响接管范围 | 需要代理的连接发生非预期直连，或 UI 在失去保护后仍声称已接管 |

选中的节点/DNS 和合法 DIRECT 属于配置的正常信任关系。风险应根据实际差异与授权范围判断，不能仅按出现 DIRECT、第三方 DNS 或外部配置认定恶意。

### 当前优先核实的失败路径

父仓库基线 `3582524` 中，[applyConfig](../../../../core/common.go) 在配置加载失败后解析并应用内建默认配置，同时继续更新监听入口。核心 [DefaultRawConfig](../../../../core/Clash.Meta/config/config.go) 使用 Rule 模式且没有用户规则和节点；普通规则未命中时，[业务路由](../../../../core/Clash.Meta/tunnel/tunnel.go)可选择 DIRECT。现有[失败用例](../../../../core/config_test.go)检查了报告错误后监听继续存在，没有证明实际业务请求的安全出口。

这是源码确认的失败路径及待验证的直连风险，尚未证明用户设备发生泄漏。L1-T03 的范围保护用于应用维护请求，不能据此推导 TUN/本机代理承载的浏览流量同样受到保护。首项应沿真实配置应用和业务拨号证明该边界，并处理已证实问题。

## 解决思路

- 定义来源的信任范围，明确允许它自动更新哪些节点、规则和资源。普通变化按既定范围处理，涉及新增接收方、扩大暴露、TLS 降级、脚本能力或应用安全策略的变化进行可理解的比较与接受/拒绝；拒绝时保护可用旧配置。
- 在现有合成边界处理最终配置，明确用户选择、订阅、脚本与应用策略的优先级。检查脚本/provider 的来源、能力和资源限制，防止隐蔽新增联网或改变接受范围；不假定原始配置的所有字段直接生效。
- 沿 TUN/本机代理到核心出站走读业务数据流，核实协议处理、插件、统计和日志只完成既定用途，检查是否复制流量、增加接收方或记录不必要内容；需要的协议封装保持可用。
- 分别核实业务 DNS、代理节点启动解析、系统解析与失败回退，保留有用途的启动解析和本地服务。IPv4/IPv6、UDP 和加密 DNS 的接收方及出口与所选策略一致，不能用“使用 DoH”替代完整路径判断。
- 核实正常运行和状态过渡中的实际连接：要求代理的路径不得静默回退，允许直连或排除的路径不误报为全设备保护。沿 ServiceState 保留状态权威，避免另建 UI 状态或配置合成器。
- 若后续需要“VPN 失败即阻断全设备”能力，再确定保护范围、Android 系统设置和兼容性；当前不把全设备断网模式设为必须完成的需求。

## 推进顺序与独立交付

先处理最终配置、失败应用及业务出口，再核实 DNS 与服务状态过渡；后续分别审查业务数据处理和来源内容接受。各项任务的目标、依赖和验收出口由[任务清单](loop2_tasks.md)维护，不把整个阶段塞入首项。

L2-T01 记录订阅、本地配置、脚本与应用覆写的合成优先级，只修正与配置应用失败和实际出口有关的行为。完整 DNS 政策、来源授权交互、脚本隔离及业务数据审计各有后续任务；当前首项不预建通用策略引擎或新的生命周期权威。

每项交付都保留正常 DIRECT、接受的代理和既有分流用途。失败处理不得未经接受扩大出口，也不能把用户已经接受的正常直连全部禁止。保留旧配置或停止受影响入口的具体选择由任务设计依据真实生命周期、资源所有权与可验证行为决定。

## 收益与代价

收益是配置可持续更新，实际网络行为与用户接受的策略一致，也能识别订阅被替换或高影响变化。代价是需要维护合成优先级和安全相关字段，部分旧配置或超出授权的变更会被拒绝。

自动信任整个订阅会扩大风险，逐条节点/规则更新都人工确认会损害刷新用途。细化时根据来源委托范围和变化影响确定交互，不为了减少网络请求强行重写合法分流或更换用户 DNS。

## 范围、依赖与完成方向

- 下载、认证和应用请求策略使用 [Loop 1](../loop1/loop1_plan.md)实际成果；本轮负责内容接受、最终配置、业务路由和 DNS。L1-T03 已完成，L1-T04 暂缓；首项可用本地配置和合成目标独立设计、验证，联网下载的身份/跳转边界仍未解决，后续端到端结论须保留该限制。
- 本机监听保护归 [Loop 3](../loop3/loop3_plan.md)，解析/脚本缺陷归 [Loop 4](../loop4/loop4_plan.md)，Geo 发布数据身份归 [Loop 6](../loop6/loop6_plan.md)。新增能力要同步相应审查范围。
- 完成时正常自动更新和接受的 DIRECT/代理/DNS 均工作，超出信任范围的输入被明确处理；启动、故障、撤销和恢复行为与提示一致。
- 依据最终配置与受控连接/DNS 观察证明边界，未验证的接管范围明确说明；证据由 [Loop 7](../loop7/loop7_plan.md)绑定实际产物。
- 按[官方同步约定](../../../../CONTRIBUTING.md)保留合成层窄差异；同步时复核新增配置字段、脚本能力、DNS 回退和生命周期行为，不能用冲突解决静默改写安全策略。

任务自身的代码、文档、验证及实际产物形成独立交付，不以等待其它未指派任务作为结束条件。阶段完成需要任务清单的实际结果共同支持；单项通过不等于所有业务流量或全部 DNS 已验证。
