# Loop 1：应用外发、请求出口与本地诊断

本轮在保留订阅自动刷新、常用站点诊断和本地 bug 证据的条件下，减少非必要采集并保护请求中的敏感数据。对应[审计基线](../android_security_baseline.md) A-01、A-02、A-03、A-15。当前只 review 阶段需求和解决方向；计划确定后再拆任务，尚未实施应用整改。

## 需求与需要保留的能力

用户需要自动取得新的订阅配置，判断 Google/YouTube 等常用服务能否通过期望出口访问，并在应用出错后保存修复 bug 所需的证据。这些功能有明确用途，不能仅因“不是代理协议必需”就删除。

用户同时要求避免隐蔽采集、未允许的直连和凭据泄漏。因此本轮关注每条请求的用途、接收方、数据、触发时间与真实出口；必要联网继续可用，不需要的统计和自动查询删除。

- 订阅自动刷新与手动刷新保留，尊重逐订阅开关和周期，失败保留旧配置。
- 常用站点的可达性/延时诊断保留，目标和频率可设置，基础连通性与地区/Premium/解锁结果分别说明。
- 自动检查应用更新删除；删除决定不扩大到用户主动检查版本。
- Firebase Analytics/Crashlytics 删除，保留本地启动恢复并新增可获取崩溃证据的本地保存。
- 公网 IP/归属地、IP 质量与扫码 SDK 的具体处理按下文待定项 review。

## 风险与不整改的后果

| 风险入口 | 当前事实与待核实边界 | 不处理时可能发生什么 |
| --- | --- | --- |
| IP 与质量查询 | 默认仪表盘可触发查询，来源含 HTTP；质量接口会向多家服务提供被查 IP，hideIp 只遮罩显示 | 未打开相关网站也会产生额外可关联的查询；直连时可能暴露真实出口，隐藏显示不能阻止外发 |
| 常用站点诊断 | 已读 Google/YouTube 路径没有附浏览器登录 Cookie/订阅令牌；站点仍能看到源 IP、时间和请求特征 | 全目标自动扫描或错误出口会增加未预期接触；诊断路径正常也不能证明所有业务流量没有泄漏 |
| Firebase 与其它 SDK | Android 引入 Analytics/Crashlytics 与 ML Kit 初始化组件；ML Kit 厂商披露有诊断采集，项目实际外发待验证 | 原生 SDK 可能绕开 Dart 控制或早于 UI 初始化；只删除 Analytics 会遗漏其它采集路径 |
| 启动和出口回退 | 自动刷新/更新检查早于免责声明；未 attach、未启动/暂停状态存在 DIRECT 分支 | 在用户误以为已受代理保护时发送请求，订阅服务或诊断站点看到非预期的真实出口 |
| 凭据、跳转与错误日志 | 订阅 URL 可带令牌，代理选择日志打印完整 URL；WebDAV 等有独立客户端与跳转行为 | 凭据进入日志，或请求/备份体发给未经允许的跳转目标；应用路由检查可能被独立客户端绕过 |
| 崩溃恢复与证据 | 当前启动恢复记录主要是阶段、失败次数和退出原因，不是完整 dump 保存机制 | 删除 Crashlytics 后若不补本地证据，bug 难定位；随意保存/导出原始 dump 又可能泄露秘密 |

这里区分两类披露：订阅服务需要收到认证令牌，目标站点需要收到请求；用户没有允许的其它接收方、数据或出口才是本轮要阻止的暴露。SDK 引入和风险线索不等于已证实二维码图片、订阅或访问内容被上传。

主要依据：[启动调度](../../../../lib/bootstrap.dart)、[请求与回退](../../../../lib/common/http.dart)、[IP 质量来源](../../../../lib/common/ip_quality.dart)、[服务诊断](../../../../core/service_check.go)、[具体站点检查](../../../../core/service_rules.go)、[Android 依赖](../../../../android/common/build.gradle.kts)、[本地启动恢复](../../../../lib/common/boot_guard.dart)。SDK 披露见审计基线 A-15。

## 解决思路与取舍

### 统一应用请求边界

在现有请求、Go 包装层探测与原生 SDK 边界核实接收方和触发条件，覆盖独立 Dio、重定向、重试、后台任务及初始化。先加载用途/目标/出口状态，再允许连接；不能只在按钮点击时检查。

普通 Dio 也可能继承全局 HttpOverrides，最终出口取决于初始化和运行状态。采用本机 PROXY 字符串不能证明核心最后没有选择 DIRECT；严格出口要核实代理组、回退和实际连接。路由变化、撤销或取消后，旧连接和迟到结果不能借新状态继续外发。

收益是统一保护订阅、诊断与 WebDAV；代价是需要处理首次导入、代理故障和旧客户端兼容。应提供明确、有限的例外，不能通过删除自动刷新或每次重复确认来回避使用需求。

### 保留有用诊断，减少额外披露

常用站点按用户选择的目标和刷新方式检查，不默认扫描无关平台；基础可达性与地区/解锁结果区分，记录实际出站，避免 Premium 不可用被误解为整个网站不可访问。

IP 查询与质量查询单独决定来源及触发方式，HTTPS、最少接收方与可停止请求是基本方向。来源服务正常收到的出口信息仍是披露，减少请求数能减少额外接触；只做显示遮罩没有网络保护效果。

诊断能帮助定位网络故障，但频繁测试会增加耗电、流量与站点记录。诊断结果只证明受测请求，业务流量/DNS 的完整保护归 Loop 2。

### 保留自动刷新，保护认证与失败路径

按逐订阅开关与周期持续运行，正常升级保留已有设置，目标/出口可用后刷新。只向所选订阅服务提供必要认证，限制跨源跳转的 token/header/body，常规日志脱敏；下载或验证失败保留旧配置。

节点全部失效时，严格代理可能暂时无法获取新订阅，需要按该订阅预先设置是否允许特定直连，或明确等待/手动处理。全局静默直连会泄露出口；一律禁用自动刷新又会损害更新节点的能力，两者都不能作为默认解决方案。

本轮保护下载与数据传输；订阅内容是否安全、合成后能否应用由 Loop 2 决定。

### 删除采集，保存本地崩溃证据

删除 Firebase 的依赖、初始化、设置和构建上传路径，并核实最终 APK 没有被传递依赖重新引入。其它 SDK，尤其扫码路径，分别核验采集与离线能力；是否发生项目外发不能只依据厂商描述判断。

本地“恢复”是避免启动失败循环，不能代替 dump。保留该能力，并保存可获得的 Dart/Java 堆栈、Go/Rust/native 线索、系统 ANR trace/tombstone、版本/进程/ABI/Build ID；同次构建在本地保留可用 mapping/符号，便于修复 bug。

Android API 30 起提供退出信息和可用 ANR trace，API 31 起可读取本应用原生 tombstone，系统缓存仍可能返回 null。需说明低版本和缺失报告的实际限制，不能保证每次都有完整 dump。[Android 报告边界](https://developer.android.com/reference/android/app/ApplicationExitInfo#getTraceInputStream())

报告私有保存并排除自动备份/上传，常规导出使用脱敏摘要；原始系统报告可能含内存片段，仅由用户单独选择保存/导出，不声称可以完全脱敏。完整进程内存镜像不默认采集，恢复不能顺带清掉 bug 证据。

收益是减少第三方采集且仍可定位故障；代价是需要本地存储、符号管理和报告生命周期设计。更广的数据/备份保护归 Loop 3，符号与 APK 输入对应关系归 Loop 5。

## 范围、依赖与完成方向

- 本轮负责应用自身请求、Go 包装层 IP/服务探测、SDK 采集、凭据日志及本地诊断需求。配置/业务路由/DNS 归 [Loop 2](../loop2/loop2_plan.md)，本机访问与数据生命周期归 [Loop 3](../loop3/loop3_plan.md)，运行漏洞归 [Loop 4](../loop4/loop4_plan.md)，构建/资产来源归 [Loop 5](../loop5/loop5_plan.md)，Geo 身份归 [Loop 6](../loop6/loop6_plan.md)。
- 完成方向是：已确认功能正常，删除项在实际 Android 产物中消失，每条保留外发有必要数据、接收方与出口；失败、取消、迁移、重定向不会绕过边界，本地可获取证据能跨启动保存。
- 验证要结合源码路径、最终包与受控网络/接收端观察，不以编译成功、隐藏 IP、无几分钟流量或界面显示代理开启作为安全证明。实际条件与剩余限制由 [Loop 7](../loop7/loop7_plan.md)汇总。
- 外部浏览器的网络出口不由应用完全控制；被选中的代理、DNS、订阅服务和目标网站仍有各自必要的元数据可见范围，不能承诺匿名上网。
- 官方同步与冲突处理遵循 [CONTRIBUTING.md](../../../../CONTRIBUTING.md)。优先保持请求与生命周期原有职责，按行为做窄改动，后续回归要能发现上游重新引入被删除功能或回退路径。

## Review 后的接续

先确定表中的未决产品选择和阶段边界，再拆可独立验证的任务。此轮不保留提前编写的任务清单，也不开始实现或编译；已确认的删除/保留决定持续有效，新的技术细节需要与这些需求一致。
