# L1-T13 正式联网用途清单 Plan

任务入口：[L1-T13](loop1_tasks.md#l1-t13-增加并核对正式联网用途清单)。建立按用途查询的 Android 联网清单，
把当前行为、实际证据和未知范围对应起来；本项不修改生产行为，也不以清单替代全应用安全验收。

## 问题与目标

用户需要判断“刷新订阅、检查 IP、运行代理或导出报告时，谁向哪里发送什么”。现有规则和交付证据分散，
仅搜索 URL 无法覆盖配置驱动的目标、Core 内部请求及系统提供方。共同判断沿用
[安全需求](../security_requirements.md#正常联网与额外暴露的判定)，不把正常服务的必要数据当成额外采集。

调查已确认：[RequestSession](../../../../lib/common/request.dart)管理应用请求的资格、出口和取消，
[WebDAV](../../../../lib/common/webdav.dart)另有认证与跳转循环；
[Core hub](../../../../core/hub.go)及 mihomo 的 resource/updater 有各自的请求作用域。
这些机制不能直接证明所有业务流量、DNS、协议握手或外部应用均受同一保护。
扫码、IP、恢复和报告的有效契约分别引用既有主题文档，不在清单重新定义。

交付应让读者从功能找到触发者、执行者、接收范围、必要数据及失败行为，并看清证据是否覆盖该条件。
Firebase、ML Kit、自动版本检查删除未回流，以及本地扫码/报告是否自行上传，须由源码、初始化/依赖与最终包交叉核对。

## 方案与理由

新增稳定主题 `docs/features/security/android_network_inventory.md`，以简短用途索引连接各用途说明。
每类统一回答：手动/自动触发和取消资格；执行者与接收方类别、公开默认来源；URL/查询、正文、UA、认证等数据；
Auto/代理/直连、TLS/HTTP/redirect；失败、缓存与重试；源码/契约及适用证据。配置 URL 使用占位说明，
不写实际订阅、凭据或流量；条件候选来源与一次执行实际访问的接收方分别描述。

| 执行归属 | 必须核对的用途 | 关键边界 |
| --- | --- | --- |
| 应用请求 | 订阅、脚本下载、WebDAV、手动更新、站点/IP、Geo | UI/调度→实际消费者；默认与配置分开 |
| Core | 业务、DNS、握手、provider/规则/Geo、健康检查、NTP/控制接口下载 | managed/unmanaged 与配置条件分开 |
| 原生/依赖及系统移交 | 初始化、网络监听、扫码/报告、IPC、浏览器、相册/SAF | 权限/依赖不证明上传；系统提供方另列 |

沿入口向下追消费者，同时从 HTTP/Dial/DNS、插件注册及初始化反查调用者，形成有限的候选根覆盖记录。
每个候选归入用途、确认未启用/不可达的依据，或显式未知；不能仅凭未发现字符串、短时零流量或依赖缺席结案。
脚本下载与执行分开，用户选择云提供方后的系统行为与应用自动上传分开。
Core 动态路径核对实际配置接入与编译条件，不能把源码中所有 adapter 都说成当前包已启用。
当前 T12 Go buildinfo 为 `with_gvisor`，仍须结合工厂和调用链判断。

选择一份用途文档而非逐 URL 台账或新增审计框架：目标和请求会随配置变化，用途与执行归属更稳定，
且能引用现有契约。具体版本、命令、结果与覆盖缺口放在本项 Result；原始搜索、依赖图、反例日志留本地忽略目录。
发现既有缺陷时记录影响和负责后续任务；若实质违背关键保护，立即交 M 判断，不在本项顺手改生产。

## 实施与验证

设计通过后按以下顺序交付；本次设计阶段仅修改本 Plan 与共享 Tasks，不运行产品测试或构建。

1. 先建立 `docs/features/security/android_network_inventory.md` 的用途与证据分层基线，待核实处明确标记；
   修改 `docs/features/security/loop1/loop1_plan.md` 中受实际交付影响的当前 Firebase/扫码表述及用途清单入口，
   同步 `docs/features/security/loop1/loop1_tasks.md` 的本项入口与阶段。
   共同需求和既有长期契约保持单一权威，历史 Plan/Result 不沿任务链回写。
2. 完成双向调用调查及证据适用性核对，再补足必要的本地受控验证；不新增运行期开关、生产模块或通用 CI。
   测试若存在真实缺口，优先使用临时合成夹具驱动真实消费者，必要输入与命令随 Result 保留可复现入口。
3. 新增 `docs/features/security/loop1/l1_t13_result.md` 记录实际覆盖、版本、偏差与限制；回填清单的已知事实并交实现评审。
   两道评审通过后依既有约定本地提交合入，M 另行完成文档清理与远端交付。

| 需证明的边界 | 方法与预期观察 |
| --- | --- |
| 刷新/脚本/WebDAV/手动更新 | 真实消费者及 localhost 成功/失败端观察数据、认证、跳转、重试；取消/换源后迟到结果无效 |
| Auto/代理/直连及 bootstrap | 按实际状态条件核对正常出口、拒绝与失效；局部诊断的严格 TLS/禁止跳转或失败不回退规则不推广到普通请求 |
| 站点/IP 诊断 | 核对实际候选选择、条件分支、缓存/限流及取消；固定公共 UA、IP 披露和目标分别按消费者验证，不把本地响应证明成外部服务协议实测 |
| Core 动态请求 | 配置→实际消费者及请求/业务作用域；正常、失败与 owner 失效；原生/协议缺口单列 |
| 依赖/初始化与删除项 | 锁定依赖、插件注册、manifest、DEX/R8、原生库和构建条件对齐；核对可达上传者及删除项 |
| 扫码/报告及系统移交 | 本地处理、原文隔离、导出及无应用上传调用；外部提供方另列，夹具不代替设备/云端验收 |

优先复用版本和条件仍适用的正式证据，记录来源、当前源码差异与适用范围；失效部分才补验。
